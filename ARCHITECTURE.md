# 🏛️ VAULT — Архитектура проекта

Этот документ подробно описывает устройство проекта: слои, потоки данных, схему БД, алгоритмы игр, взаимодействие по WebSocket и cron-задачи.

---

## 0. Запуск на Windows / macOS / Linux

Проект запускается одной командой `docker-compose up --build` на любой ОС.

**Важно для Windows:** убедитесь что в Docker Desktop разрешён File Sharing для диска, где лежит проект (Settings → Resources → File Sharing → поставить галочку на диске C:).

Инициализация БД не использует bind-mount с хоста (чтобы избежать ошибок доступа к файлам на Windows): для PostgreSQL сделан отдельный Dockerfile в папке `db/`, который копирует `init.sql` внутрь образа на этапе сборки.

### 2.3 Авторизация во фронте
1. При открытии приложения `App.tsx` читает токен из `localStorage('vault_token')`
2. Если токена нет — проверяет `window.Telegram.WebApp.initData`:
   - В проде — передаёт реальный initData на бэкенд
   - В демо (браузер без Telegram) — генерирует `demo:<telegram_id>:<username>` и регистрирует тестового пользователя
3. JWT сохраняется в localStorage и подставляется в `Authorization` через api-client
4. Инициализируется Socket.io с токеном в `auth`, что позволяет серверу джойнить юзера в комнату `user:<id>` для персональных уведомлений

### 2.4 Принципы UX (по ТЗ)
- Максимальный контейнер — 480-520px (имитация экрана телефона на десктопе)

- Баланс — самый крупный текст на главной (48px)

## 3. Backend

### 3.1 Стек
- **Express 4** — HTTP сервер
- **Socket.io 4** поверх http сервера — и игровой канал ракеты, и общие уведомления
- **node-cron** — расписание крон-задач
- **pg** — нативный клиент PostgreSQL (пулинг соединений)
- **ioredis** — клиент Redis (для кэша и сессий; зарезервирован под будущий rate-limiting)
- **bcryptjs** — хеширование PIN
- **jsonwebtoken** — JWT авторизация
- **telegraf** — телеграм-бот (в отдельном контейнере, может быть и встроен)
- **@ton/ton, @ton/core, @ton/crypto** — зависимости для реальной интеграции (используются в демо-режиме как заглушки, закомментированные места)

### 3.2 Слои (важный архитектурный принцип!)

```
REST routes  (api/routes/*.ts)
   │   только HTTP: парсинг тела, вызов сервисов, форматирование ответа
   │   НИКАКОЙ бизнес-логики!
   ▼
Services (services/*.ts)
   │   ВСЯ бизнес-логика: расчёты, изменения в БД, кэшауты, начисления
   │   Один сервис = одна предметная область (rocket, duel, safe, ...)
   │   Единственный способ менять баланс — modifyBalance() в services/balance.ts
   ▼
DB layer (db/pool.ts, db/redis.ts)
   │   Только соединения и низкоуровневые запросы
   ▼
PostgreSQL + Redis
```

**WebSocket слой** (`websocket/rocket.ts`) общается с сервисами аналогично REST, но работает в реальном времени.

**Cron слой** (`cron/index.ts`) по расписанию вызывает сервисы + broadcast через notifications.

### 3.3 Важные инварианты
1. **Единственная функция изменения баланса** — `modifyBalance(userId, amount, type, opts)`. Она:
   - Обновляет баланс в транзакции
   - Пишет запись в `transactions` с новым остатком
   - Обновляет `last_active`

2. **Банкролл Ракеты** обновляется через `updateRocketBankroll(delta)` внутри `placeBet` и `processCashout` — нет других точек входа (кроме админки).

3. **Все комиссии** рассчитываются и распределяются строго в сервисах на моменте ставки/депозита:
   - 90% в игру
   - 3% рефоводу (или админу если нет рефа)
   - 7% доход админа (учитывается в `daily_revenue`)

4. **Настройки платформы** (комиссии, проценты, лимиты) хранятся в таблице `settings` и читаются через `getSetting()` — не захардкожены.

### 3.4 WebSocket

События клиент → сервер:
| Событие | Payload | Назначение |
|---------|---------|------------|
| `rocket:join` | `roundId` | Войти в комнату раунда для получения тиков |
| `rocket:launch` | `{ round_id, crash_at }` | Подтвердить готовность, сервер стартует тики |
| `cashout` | `{ elapsed }` | Попытка забрать выигрыш |

События сервер → клиент:
| Событие | Payload | Назначение |
|---------|---------|------------|
| `tick` | `{ multiplier, elapsed }` | Очередной кадр полёта (50ms интервал = 20 FPS) |
| `crash` | `{ crash_at }` | Ракета взорвалась |
| `cashout_result` | `{ result, cashout_at, crash_at, profit }` | Результат кэшаута |
| `notification` | `{ message, data }` | Персональное уведомление |
| `safe_crack_started`, `safe_finished`, `vault_distributed` | — | Глобальные события крон-задач |

Подключение идентифицируется по JWT (в `auth.handshake`), клиент автоматически джойнится в комнату `user:<id>`, после чего все серверные вызовы `notify(userId, ...)` доходят до нужного сокета.

### 4.2 Денежные потоки (транзакции)

Все суммы в БД хранятся как `DECIMAL(12,2)` (2 знака после запятой — точность центов USDT). Никогда не используем `float` в финансовых расчётах — все вычисления в JS округляются через `Math.round(x * 100) / 100`.

Пример: ставка $10 в Ракету → что происходит:
1. `modifyBalance(user, -10, 'bet')` → баланс -10, запись в transactions
2. Комиссия 10% = $1
   - 90% = $9 → `updateRocketBankroll(+9)`
   - 3% = $0.30 → рефоводу (если есть) через `modifyBalance(referrer, 0.30, 'referral')`
   - 7% = $0.70 (или $1 если нет рефа) → `logPlatformRevenue(0.70, 'rocket')`
3. Создаётся запись в `rocket_rounds` с предрассчитанным `crash_at`

### 4.3 Функция округления лимитов

```typescript
// backend/src/config.ts
function roundDownClean(value: number): number {
  if (value < 10) return Math.max(1, Math.floor(value));
  const digits = Math.floor(value).toString().length;
  const power = Math.pow(10, digits - 1);
  return Math.floor(value / power) * power;
}
```

Примеры: `33→30`, `68→60`, `116→100`, `288→200`, `1437→1000`, `14000→10000`.

Применяется к:
- Максимальной ставке Ракеты: `roundDownClean(bankroll × 0.5)`
- Максимальному Вкладу: `roundDownClean(max(pool × 10, 100))`

## 5. Игровые алгоритмы

### 5.1 Ракета 🚀

**Кривая роста множителя:**
```
x(t) = e^(0.075 × t)
```
- 0с → x1.00, 2с → x1.16, 9с → x1.97, 10с → x2.12
- 15с → x3.08, 20с → x4.48, 30с → x9.49, 60с → x90.02

**Точка взрыва** рассчитывается в `calculateCrashPoint(bet, bankroll)`:
```typescript
function calculateCrashPoint(bet, bankroll) {
  const maxByBankroll = bankroll / bet;          // защита кассы — не можем выплатить больше банка
  const r = Math.random();
  const randomCrash = 0.90 / (1 - r);            // 10% house edge: R = 0.9/(1-r) → E[R] = ∞, но P(R≥x) = 0.9/x → house edge 10%
  const crash = Math.min(randomCrash, maxByBankroll);
  return Math.max(Math.round(crash * 100) / 100, 1.01);
}
```

Почему `0.9/(1-r)` даёт 10% house edge:
- P(крах ≥ x) = P(0.9/(1-r) ≥ x) = P(r ≥ 1 - 0.9/x) = 0.9/x
- Матожидание выплаты при ставке 1 и авто-кэшауте на x: x × P(успеть) = x × 0.9/x = 0.9 → 10% комиссии.

**Красивые полёты** (3% случаев): если игрок вышел рано (забрал на x < 5), с шансом 3% после кэшаута `crash_at` заменяется на красивое число 20-80. Игрок не получает дополнительных денег, но визуально ракета летит дальше и взрывается очень высоко — создаёт FOMO.

### 5.2 Дуэль ⚔️

1. Создатель вызывает `POST /duel/create {amount}` — средства списываются и замораживаются (frozen_balance += amount, balance -= amount)
2. Создаётся запись в `duels` со статусом `waiting`
3. Появляется в лобби для всех
4. Оппонент нажимает «Принять»:
   - Проверяется, что у оппонента хватает баланса
   - Списывается его ставка, размораживается ставка создателя
   - `result = Math.random() < 0.5 ? 'heads' : 'tails'`
   - Победитель: `heads` → создатель, `tails` → оппонент (детерминировано: орёл = создатель, решка = оппонент)
   - Банк 2×amount, комиссия 10% → приз победителю 2×amount×0.9 = 1.8×amount
   - С каждого игрока отдельно распределяется комиссия: 3% рефоводу + 7% платформе
   - Генерируется случайная траектория монеты: `{ rotation_speed, height, bounces, final_angle }`
   - Фронтенд получает результат и воспроизводит 3D-анимацию по этим параметрам

### 5.3 Сейф 🔒

**Ежедневный цикл:**
1. **09:00** — создаётся запись в `safes` на сегодня. Если 3+ дня подряд статус не `finished` — устанавливается `bonus=true` (комиссия 5% вместо 10%). Генерируется случайный код `[0-9, 0-9, 0-9]` и скорости барабанов `[1.5-4.0 об/с, ...]`.
2. **Весь день (collecting)** — пользователи вносят средства:
   - Сразу снимается комиссия (10% или 5% при бонусе)
   - 90%/95% уходит в `prize_pool`
   - Комиссия распределяется на рефовода и платформу
   - Пользователь может отменить вклад до 21:00 (возврат body на баланс)
3. **21:00** — проверяется минимум (банк ≥ $25, участников ≥ 2):
   - Если не собран — все вклады возвращаются, сейф получает статус `cancelled`
   - Если собран — статус `cracking`, проставляется `crack_started_at`, создаётся сейф на следующий день, клиентам показываются барабаны и код
4. **21:00 → 21:00 + окно взлома** — фаза взлома. Окно длится **ровно** `safe_crack_timeout_minutes` (настройка в админке, по умолчанию 2 минуты) — это дедлайн для всех участников:
   - Пользователи тапают по барабанам в момент, когда видна нужная цифра, фронтенд отправляет `{ time_ms }`
   - Сервер пишет `max(время клиента, время от crack_started_at)` — так что клиентские часы нельзя «подкрутить» и победители честно сортируются по моменту сдачи
   - Результат сдаётся один раз: повторный `POST /api/safe/crack` не перезаписывает уже засчитанное время (возвращает `already_recorded`), поэтому возврат на экран взлома не ухудшает и не «перезапускает» игру
   - `/api/safe/current` отдаёт `crack_window_ms`, `crack_remaining_ms` (обратный отсчёт) и `pending_cracks` (сколько участников ещё не сдали → «Ждём остальных»)
   - После закрытия окна сервер принимает результат ещё 5 секунд (`CRACK_GRACE_MS`) — допуск на доставку того, что игрок отправил до дедлайна; клиенту этот запас не показывается
5. **Итоги подводятся сразу, как только результат сдали ВСЕ участники** (обычно через 5–20 секунд), — ждать конца окна не нужно. Если кто-то ушёл от компьютера, взлом закрывается по дедлайну, а не сдавшему достаётся «техническое поражение»: `crack_time_ms = NULL` → «не успел», приз 0 (`finalizeCracking()` → `calculateSafeWinners()`; таймер ставит `startCracking()`, досрочно итоги вызывает `submitCrackTime()`, каждую минуту cron зовёт `finalizeCrackIfDue()` как страховку после рестарта, а при старте процесса — `resumeCracking()`):
   - Депозиты сортируются по `crack_time_ms ASC NULLS LAST` (быстрее всего → первые, не сдавшие → в конце)
   - Идём по списку и выплачиваем `amount × 1.5` пока хватает `prize_pool`
   - Следующему за ним достаётся **остаток пула** (частичный приз), всем остальным — 0
   - Так как пул = 90% банка, а выплата ×1.5, денег хватает примерно на 60% вкладов: полный ×1.5 получают самые быстрые, поэтому порядок по времени решает всё

**Защита от ботов** (в production, не демо):
- Скорости барабанов рандомизируются ежедневно и известны только серверу
- Код показывается за 1 сек до старта
- Время засчитывается как `max(client-side, серверное время от crack_started_at)`, поэтому «нарисовать» себе быстрые миллисекунды нельзя; ввод после закрытия окна отклоняется
- Время <500мс = подозрительно (бот)
- Промах по цифре = +0.5 сек штрафа

### 5.4 Vault Вклад 💎

Множители: `{1: 1.0, 7: 1.3, 14: 1.6, 30: 2.0}`

**Блокировка:**
- Проверяется мин. $10, макс. = `vault_max_deposit`
- Средства замораживаются (frozen_balance += amount)
- Создаётся запись `vault_deposits` со статусом `active`

**Ежесуточное распределение в 00:00 (`dailyVaultDistribution()`):**
1. Берётся `revenue` — сумма ВСЕХ записей `daily_revenue` за вчера (это УЖЕ чистый доход после выплаты рефералов)
2. Автопул = revenue × 15% (`vault_pool_percent`)
3. Ручной пул = `manual_pool_addition` (из настроек, добавленное админом за день)
4. Обнуляем `manual_pool_addition` после снятия
5. Суммарный пул = auto + manual
6. Для каждого активного вклада считаем вес: `weight = amount × multiplier`
7. Суммарный вес `totalWeight = sum(weight)`
8. Каждый вклад получает: `daily_profit = pool × weight / totalWeight`
9. `days_elapsed += 1`
10. Если срок истёк (`days_elapsed >= term_days`):
    - Выплачиваем `amount + accumulated_profit` на баланс
    - Размораживаем тело
    - Ставим статус `completed`
11. Пересчитываем новый `vault_max_deposit = roundDownClean(max(pool × 10, 100))`
12. Сохраняем статистику дня в `vault_pool_daily` (базовая ставка = pool/total_locked)

**Досрочный выход:**
- Доступен только для сроков > 1 дня
- Тело возвращается на баланс (размораживается)
- `accumulated_profit` не выплачивается (сгорает)
- Статус становится `early_unlock`

## 6. Cron-задачи

| Время (UTC, сервер) | Задача | Файл/функция |
|--------------------|--------|-------------|
| `0 6 * * *` (09:00 МСК) | Создать дневной Сейф (с проверкой бонус-режима) | `cron` → `services/safe.createDailySafe()` |
| `* * * * *` (каждую минуту) | Старт взлома в настроенное время МСК (`safe_crack_hour`/`safe_crack_minute`, в т.ч. догоняюще после простоя) + страховка закрытия истёкшего окна взлома | `cron` → `services/safe.startCracking()` / `finalizeCrackIfDue()` |
| по таймеру окна взлома | Подвести итоги Сейфа, распределить призы ×1.5 по скорости | `services/safe.finalizeCracking()` → `calculateSafeWinners()` |
| при старте процесса | Восстановить таймер незавершённого взлома после рестарта | `services/safe.resumeCracking()` |
| `0 0 * * *` (00:00) | Дневное распределение Вклада, выплаты истёкших вкладов, пересчёт макс. вклада | `cron/vault-deposit.dailyVaultDistribution()` |

> ⚠️ В продакшене часовой пояс сервера нужно настроить на Europe/Moscow (UTC+3) или считать время относительно пользовательского часового пояса. В MVP используется системное время сервера.

## 7. Безопасность

1. **PIN-код вывода** — 4 цифры, хранится как bcrypt-хеш, никогда не возвращается клиенту.
2. **JWT** — подписывается секретом из конфига (`jwtSecret`), срок жизни 30 дней.
3. **Авторизация middleware** — на каждый эндпоинт проверяется `Authorization` заголовок, в запрос подставляется объект пользователя `req.user`.
4. **Админ-доступ** — отдельный middleware `adminOnly`, проверяющий что `telegram_id` пользователя входит в `ADMIN_TELEGRAM_IDS` из переменных окружения.
5. **Денежные операции идут в SQL-транзакциях** (`BEGIN/COMMIT/ROLLBACK`) — см. `modifyBalance()`. Это гарантирует, что баланс и запись в `transactions` обновятся одновременно.
6. **Демо-режим** флаг `DEMO_MODE=true` отключает реальные TON-операции и позволяет вход по `demo:<id>:<username>`, что должно быть отключено в проде.

Что нужно добавить в проде (помечено TODO):
- Проверка подписи Telegram initData по алгоритму HMAC-SHA256 с bot_token
- Rate-limiting (настройки для каждого эндпоинта указаны в ТЗ: rocket_start 10/мин, withdraw 3/час, общее 60/мин)
- ~~Серверный замер времени взлома Сейфа (а не client-side)~~ — сделано: `crack_started_at` + `max(client, server)` в `submitCrackTime()`
- Детекция мультиаккаунтов: один TON-адрес вывода = один аккаунт
- Хранение JWT-секрета не в коде, а в переменной окружения

## 8. 3D-сцены (Three.js)

## 10. Поток запуска приложения (на примере Ракеты)

1. Игрок открывает `/rocket`, видит ставку $10 → нажимает «🚀 ЗАПУСТИТЬ»
2. Фронт → `POST /api/rocket/start {bet:10}`
3. Бэкенд в `services/rocket.placeBet()`:
   - Проверяет лимиты (мин $1, доступный баланс, max_bet по кассе)
   - Списывает $10 с баланса через `modifyBalance()` (пишет транзакцию)
   - Распределяет комиссию ($9 в кассу, $0.30 рефоводу, $0.70 в доход платформы)
   - Генерирует `crash_at` по алгоритму
   - Создаёт `rocket_rounds` запись
   - Возвращает `{ round_id, crash_at, max_bet }`
4. Фронт переключает сцену в режим «flying», отображает 3D ракету
5. Фронт подключается к `/rocket` namespace Socket.io и отправляет `rocket:join` и `rocket:launch`
6. Сервер в `websocket/rocket.startRocketRound()` запускает setInterval 20 FPS:
   - Рассчитывает `mult = e^(0.075 * elapsed)`
   - Шлёт `tick` в комнату раунда
   - При достижении `mult >= crashAt` — вызывает `processCrash()`, шлёт `crash`
7. Игрок нажимает «💰 ЗАБРАТЬ»:
   - Фронт шлёт `cashout {elapsed}` (доверительный, но сервер перепроверяет по своему времени)
   - Сервер в `processCashout()` проверяет что текущий mult < crashAt
   - Выплачивает gross_win = bet × mult через modifyBalance
   - Снимает gross_win из кассы Ракеты
   - С 3% шансом подменяет crash_at на «красивый» (20-80)
   - Возвращает результат
   - Шлёт окончательный `crash` с финальной точкой
8. Фронт показывает экран результата (выигрыш или проигрыш), догружает историю

## 11. Масштабирование и дальнейшая разработка

### Куда добавлять новую игру (рецепт)
1. Добавьте таблицу в `db/init.sql` (например, `mines_rounds`)
2. Создайте сервис в `services/mines.ts` с функциями placeBet, reveal, cashout — используйте `modifyBalance()` и `logPlatformRevenue()` для учёта комиссии
3. Добавьте REST routes в `api/routes/mines.ts` и зарегистрируйте в `index.ts`
4. Если нужен реалтайм — создайте websocket-обработчик в `websocket/mines.ts` и зарегистрируйте в `index.ts`
5. Добавьте cron-задачи если игра имеет периодическую логику
6. Добавьте экраны в `components/mines/` и Three.js сцену в `three/mines/`
7. Добавьте плитку игры на главный экран `components/layout/Home.tsx`
8. Добавьте роут в `App.tsx`

### Куда править комиссии и лимиты
Все правки — **только через админ-панель** или напрямую в таблице `settings`. Никогда не хардкодьте цифры в сервисах; всегда читайте через `getSetting()`.

### Добавление нового уведомления
Используйте `notify(userId, message, data)` из `services/notifications.ts` — оно автоматически дойдёт до подключённого сокета пользователя как событие `notification`. Для Telegram-уведомлений в проде расширьте эту функцию вызовом `bot.telegram.sendMessage(userId, message)`.
