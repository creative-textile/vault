Этот документ подробно описывает устройство проекта: слои, потоки данных, схему БД, алгоритмы игр, взаимодействие по WebSocket и cron-задачи.

## 0. Запуск на Windows / macOS / Linux

Проект запускается одной командой `docker-compose up --build` на любой ОС.

**Важно для Windows:** убедитесь что в Docker Desktop разрешён File Sharing для диска, где лежит проект (Settings → Resources → File Sharing → поставить галочку на диске C:).

Инициализация БД не использует bind-mount с хоста (чтобы избежать ошибок доступа к файлам на Windows): для PostgreSQL сделан отдельный Dockerfile в папке `db/`, который копирует `init.sql` внутрь образа на этапе сборки.

**Обновление фронта после деплоя.** `index.html` отдаётся с `Cache-Control: no-store, no-cache` (см. `frontend/nginx.conf`): без явных заголовков браузер кеширует его эвристически по `Last-Modified` и после пересборки показывает старую страницу со ссылками на старые хешированные бандлы — изменения «не применяются», хотя образ пересобран. Сами `.js`/`.css` кешируются на 30 дней с `immutable`: их имена содержат хеш содержимого и меняются на каждой сборке. Метка сборки вшивается в бандл (`define: __BUILD_INFO__` в `vite.config.ts`) и показана внизу профиля — «сборка фронтенда: 2026-09-12 14:59 UTC». Если после деплоя дата старая, проблема в кеше браузера, а не в коде: один раз нажмите `Ctrl+Shift+R`.

**Смоук-тесты** (`cd backend && npm test`, т.е. `node tests/smoke.cjs`) не требуют ни Docker, ни живой БД — всё считается в `pg-mem` (dev-зависимость). Режимы: `dates` (арифметика дат и часовые пояса), `chain` (цепочка раундов не обрывается), `crack` (приём результата взлома), `http` (маршруты, витрина, настройки, токены). Каждый режим поднимает свою БД, поэтому `npm test` гоняет их по очереди в отдельных процессах.

### 2.3 Авторизация во фронте
1. При открытии приложения `App.tsx` читает токен из `localStorage('vault_token')`
2. Если токена нет — проверяет `window.Telegram.WebApp.initData`:
   - В проде — передаёт реальный initData на бэкенд
   - В демо (браузер без Telegram) — генерирует `demo:<telegram_id>:<username>` и регистрирует тестового пользователя
3. JWT сохраняется в localStorage и подставляется в `Authorization` через api-client
4. Инициализируется Socket.io с токеном в `auth`, что позволяет серверу джойнить юзера в комнату `user:<id>` для персональных уведомлений

- Максимальный контейнер — 480-520px (имитация экрана телефона на десктопе)

- Баланс — самый крупный текст на главной (48px)

## 3. Backend

### 3.1 Стек
- **Express 4** — HTTP сервер
- **Socket.io 4** поверх http сервера — и игровой канал ракеты, и общие уведомления
- **node-cron** — расписание крон-задач
- **pg** — нативный клиент PostgreSQL (пулинг соединений)
- **ioredis** — клиент Redis (для кэша и сессий; зарезервирован под будущий rate-limiting)
- **bcryptjs** — хеширование PIN
- **jsonwebtoken** — JWT авторизация
- **telegraf** — телеграм-бот (в отдельном контейнере, может быть и встроен)
- **@ton/ton, @ton/core, @ton/crypto** — зависимости для реальной интеграции (используются в демо-режиме как заглушки, закомментированные места)

### 3.2 Слои (важный архитектурный принцип!)

```
REST routes  (api/routes/*.ts)
   │   только HTTP: парсинг тела, вызов сервисов, форматирование ответа
   │   НИКАКОЙ бизнес-логики!
   ▼
Services (services/*.ts)
   │   ВСЯ бизнес-логика: расчёты, изменения в БД, кэшауты, начисления
   │   Один сервис = одна предметная область (rocket, duel, safe, ...)
   │   Единственный способ менять баланс — modifyBalance() в services/balance.ts
   ▼
DB layer (db/pool.ts, db/redis.ts)
   │   Только соединения и низкоуровневые запросы
   ▼
PostgreSQL + Redis
```

**WebSocket слой** (`websocket/rocket.ts`) общается с сервисами аналогично REST, но работает в реальном времени.

**Cron слой** (`cron/index.ts`) по расписанию вызывает сервисы + broadcast через notifications.

### 3.3 Важные инварианты
1. **Единственная функция изменения баланса** — `modifyBalance(userId, amount, type, opts)`. Она:
   - Обновляет баланс в транзакции
   - Пишет запись в `transactions` с новым остатком
   - Обновляет `last_active`

2. **Банкролл Ракеты** обновляется через `updateRocketBankroll(delta)` внутри `placeBet` и `processCashout` — нет других точек входа (кроме админки).

3. **Все комиссии** рассчитываются и распределяются строго в сервисах на моменте ставки/депозита:
   - 90% в игру
   - 3% рефоводу (или админу если нет рефа)
   - 7% доход админа (учитывается в `daily_revenue`)

4. **Настройки платформы** (комиссии, проценты, лимиты) хранятся в таблице `settings` и читаются через `getSetting()` — не захардкожены. `GET /api/admin/settings` вместе со значениями и подписями отдаёт `groups` — разделы («🔒 Сейф», «🚀 Ракета», «💎 Вклад (VAULT)», «💰 Комиссии и рефералы», «📊 Проект»), по которым админ-панель раскладывает поля: сплошной список из 14 настроек было невозможно читать. Поля, не попавшие ни в одну группу, попадают в раздел «🧩 Прочее», поэтому новая настройка не потеряется.

5. **Токен привязан к человеку, а не к номеру строки.** JWT несёт и `userId`, и `telegramId`; `getUserFromToken()` сверяет `telegram_id` из БД с `telegram_id` из токена и при несовпадении возвращает `null` → клиент получает 401 и входит заново. Без этой проверки старый токен, сохранённый в другом браузере, после пересоздания БД «садился» в чужой аккаунт с тем же `id`: человек видел чужой баланс и играл чужой вклад. Токены старого формата (без `telegramId`) продолжают работать. Та же функция используется в `io.use()` — сокет с недействительным токеном не попадает в комнату `user:<id>` и не получает чужие уведомления и `balance_updated`.

### 3.4 WebSocket

События клиент → сервер:
| Событие | Payload | Назначение |
|---------|---------|------------|
| `rocket:join` | `roundId` | Войти в комнату раунда для получения тиков |
| `rocket:launch` | `{ round_id, crash_at }` | Подтвердить готовность, сервер стартует тики |
| `cashout` | `{ elapsed }` | Попытка забрать выигрыш |

События сервер → клиент:
| Событие | Payload | Назначение |
|---------|---------|------------|
| `tick` | `{ multiplier, elapsed }` | Очередной кадр полёта (50ms интервал = 20 FPS) |
| `crash` | `{ crash_at }` | Ракета взорвалась |
| `cashout_result` | `{ result, cashout_at, crash_at, profit }` | Результат кэшаута |
| `notification` | `{ message, data }` | Персональное уведомление |
| `safe_crack_started`, `safe_finished`, `vault_distributed` | — | Глобальные события крон-задач |
| `balance_updated` | `{ balance, frozen_balance }` | Личное событие (комната `user:<id>`): шлётся из `modifyBalance()` после каждой операции с деньгами, чтобы баланс на экране менялся сразу, а не по следующему опросу `/api/profile`. `App.tsx` обновляет стор, все экраны (главная, хедер, игры) видят новую цифру мгновенно |

Подключение идентифицируется по JWT (в `auth.handshake`), клиент автоматически джойнится в комнату `user:<id>`, после чего все серверные вызовы `notify(userId, ...)` доходят до нужного сокета.

### 4.2 Денежные потоки (транзакции)

Все суммы в БД хранятся как `DECIMAL(12,2)` (2 знака после запятой — точность центов USDT). Никогда не используем `float` в финансовых расчётах — все вычисления в JS округляются через `Math.round(x * 100) / 100`.

Пример: ставка $10 в Ракету → что происходит:
1. `modifyBalance(user, -10, 'bet')` → баланс -10, запись в transactions
2. Комиссия 10% = $1
   - 90% = $9 → `updateRocketBankroll(+9)`
   - 3% = $0.30 → рефоводу (если есть) через `modifyBalance(referrer, 0.30, 'referral')`
   - 7% = $0.70 (или $1 если нет рефа) → `logPlatformRevenue(0.70, 'rocket')`
3. Создаётся запись в `rocket_rounds` с предрассчитанным `crash_at`

### 4.3 Функция округления лимитов

```typescript
// backend/src/config.ts
function roundDownClean(value: number): number {
  if (value < 10) return Math.max(1, Math.floor(value));
  const digits = Math.floor(value).toString().length;
  const power = Math.pow(10, digits - 1);
  return Math.floor(value / power) * power;
}
```

Примеры: `33→30`, `68→60`, `116→100`, `288→200`, `1437→1000`, `14000→10000`.

Применяется к:
- Максимальной ставке Ракеты: `roundDownClean(bankroll × 0.5)`
- Максимальному Вкладу: `roundDownClean(max(pool × 10, 100))`

## 5. Игровые алгоритмы

### 5.1 Ракета 🚀

**Кривая роста множителя:**
```
x(t) = e^(0.075 × t)
```
- 0с → x1.00, 2с → x1.16, 9с → x1.97, 10с → x2.12
- 15с → x3.08, 20с → x4.48, 30с → x9.49, 60с → x90.02

**Точка взрыва** рассчитывается в `calculateCrashPoint(bet, bankroll)`:
```typescript
function calculateCrashPoint(bet, bankroll) {
  const maxByBankroll = bankroll / bet;          // защита кассы — не можем выплатить больше банка
  const r = Math.random();
  const randomCrash = 0.90 / (1 - r);            // 10% house edge: R = 0.9/(1-r) → E[R] = ∞, но P(R≥x) = 0.9/x → house edge 10%
  const crash = Math.min(randomCrash, maxByBankroll);
  return Math.max(Math.round(crash * 100) / 100, 1.01);
}
```

Почему `0.9/(1-r)` даёт 10% house edge:
- P(крах ≥ x) = P(0.9/(1-r) ≥ x) = P(r ≥ 1 - 0.9/x) = 0.9/x
- Матожидание выплаты при ставке 1 и авто-кэшауте на x: x × P(успеть) = x × 0.9/x = 0.9 → 10% комиссии.

**Красивые полёты** (3% случаев): если игрок вышел рано (забрал на x < 5), с шансом 3% после кэшаута `crash_at` заменяется на красивое число 20-80. Игрок не получает дополнительных денег, но визуально ракета летит дальше и взрывается очень высоко — создаёт FOMO.

### 5.2 Дуэль ⚔️

1. Создатель вызывает `POST /duel/create {amount}` — средства списываются и замораживаются (frozen_balance += amount, balance -= amount)
2. Создаётся запись в `duels` со статусом `waiting`
3. Появляется в лобби для всех
4. Оппонент нажимает «Принять»:
   - Проверяется, что у оппонента хватает баланса
   - Списывается его ставка, размораживается ставка создателя
   - `result = Math.random() < 0.5 ? 'heads' : 'tails'`
   - Победитель: `heads` → создатель, `tails` → оппонент (детерминировано: орёл = создатель, решка = оппонент)
   - Банк 2×amount, комиссия 10% → приз победителю 2×amount×0.9 = 1.8×amount
   - С каждого игрока отдельно распределяется комиссия: 3% рефоводу + 7% платформе
   - Генерируется случайная траектория монеты: `{ rotation_speed, height, bounces, final_angle }`
   - Фронтенд получает результат и воспроизводит 3D-анимацию по этим параметрам

### 5.3 Сейф 🔒

**Ежедневный цикл:**
1. **09:00** — создаётся запись в `safes` на сегодня. Если 3+ дня подряд статус не `finished` — устанавливается `bonus=true` (комиссия 5% вместо 10%). Генерируется случайный код `[0-9, 0-9, 0-9]` и скорости барабанов `drum_speeds` — три разных числа в диапазоне **1.45–2.00** (`generateDrumSpeeds()`: база 1.50–1.65, второй барабан +0.13…+0.20, третий +0.26…+0.36). Одна цифра видна `1000 / (speed × 1.3)` мс, т.е. **385–530 мс**: средний игрок с реакцией 250–300 мс попадает примерно в 80% попыток, но разница между игроками остаётся в миллисекундах. Старые записи со скоростями вне диапазона `normalizeSafe()` приводит к запасным `[1.55, 1.72, 1.9]` — миграция БД не нужна.
2. **Весь день (collecting)** — пользователи вносят средства (вклад всегда уходит в **собирающий сейф**, см. ниже):
   - Сразу снимается комиссия (10% или 5% при бонусе)
   - 90%/95% уходит в `prize_pool`
   - Комиссия распределяется на рефовода и платформу
   - Пользователь может отменить вклад до начала взлома (возврат body на баланс)
   - **Даты сейфов считаются строково, никогда через `Date`.** В контейнере `TZ=Europe/Moscow`, и pg отдаёт колонку `DATE` как `Date` в **локальной** полночи: `setUTCDate(+1)` + `toISOString()` сдвигает дату на день назад, следующий сейф получает сегодняшнюю дату, `INSERT` упирается в `UNIQUE(date)` и цепочка обрывается (в pg-mem `DATE` приходит строкой, поэтому баг воспроизводится только на живой БД). Помощники `toDateStr()`/`nextSafeDate()` в `services/safe.ts` берут локальные компоненты и прибавляют день через `Date.UTC` — покрытие в `smoke-cron.cjs chain`
   - **Сбор не останавливается ни на минуту, а цепочка сейфов бесконечна.** `getCollectingSafe()` возвращает первый сейф со статусом `collecting` и датой ≥ сегодня; при отсутствии его создаёт `ensureNextDaySafe()` — датой **«максимальная дата в таблице + 1 день»** (а не «календарное завтра»), иначе после переноса времени взлома «завтра» уже занято сейфом #2, `INSERT` упирается в `UNIQUE(date)`, и раунд #3 не создаётся никогда. Если сервер долго не работал, дата берётся не раньше сегодняшней. Вставка идёт с `ON CONFLICT (date) DO NOTHING`, поэтому параллельные вклады не создают два сейфа. `safeDeposit()`/`cancelSafeDeposit()` работают именно с ним, поэтому во время взлома и после розыгрыша вклады (ручные и автовклад `auto_safe_percent` с выигрыша в дуэли/ракете) уходят уже в следующий сейф и никогда не получают «Сейф закрыт»
   - Каждый вклад/возврат рассылает socket-событие `safe_deposit { safe_id, bank, prize_pool, participants_count }` — банк в карточках (главная, сейф) обновляется у всех клиентов без перезагрузки
3. **21:00** — планировщик (`maybeStartCrack()`, тик раз в минуту + `runSafeTick()` для тестов) проверяет минимум (банк ≥ $25, участников ≥ 2):
   - Если не собран — все вклады возвращаются, сейф получает статус `cancelled`
   - Если собран — статус `cracking`, проставляется `crack_started_at`, создаётся сейф на следующий день, клиентам показываются барабаны и код
   - **Ломают тот сейф, который сейчас собирает** (`getCollectingSafeOrNull()`), а не «сегодняшний»: после розыгрыша собирать уже может сейф следующей даты, и именно он должен открыться в настроенное время
   - Слот взлома — настроенные час:минута сегодняшнего дня (`todaySlotMSK()`). Если сейф начал собирать **позже** текущего слота (`collect_started_at`, для старых строк — момент взлома предыдущего сейфа), значит слот уже отыгран предыдущим раундом и взлом переносится на завтра. Отсюда два следствия: (а) нет бесконечного цикла «взлом → сбор → тут же взлом», (б) **перенос времени в админке срабатывает сразу** — собирающий сейф открывается в новый слот, ждать сутки не нужно
   - `/api/safe/current` отдаёт `crack_at`/`time_to_crack_ms` собирающего сейфа (`nextMSK()` — ближайшее наступление настроенного времени), поэтому таймер на главной и на экране сейфа всегда показывает реальный момент следующего взлома
4. **21:00 → 21:00 + окно взлома** — фаза взлома. Окно длится **ровно** `safe_crack_timeout_minutes` (настройка в админке «Нужно взломать сейф за (минуты)», по умолчанию **1 минута**; та же формулировка — в таймерах на `/safe` и `/safe/crack`) — это дедлайн для всех участников:
   - Пользователи тапают по барабанам в момент, когда видна нужная цифра, фронтенд отправляет `{ time_ms }`
   - **Код проверяет сервер.** Барабан останавливается только на своей цифре. Клиент отправляет `{ time_ms, taps: [ms, ms, ms] }` — моменты тапов от старта вращения, а сервер той же формулой `digitAt(speed, ms) = floor((ms × speed × 0.0013) % 10)` пересчитывает, какие цифры были видны, и сверяет с кодом сейфа. Если хоть одна цифра не совпала — результат **отклоняется** (`400 «Цифры не совпадают с кодом сейфа»`), клиент раскручивает барабаны заново, и игрок пробует снова. Засчитанное время = `max(заявленное клиентом, max(taps), elapsed от crack_started_at)` — «поставить любые числа» и выиграть миллисекунды больше нельзя; отклонения пишутся в лог
   - **Штрафного времени за промах нет** (прежде тап мимо добавлял +0.5 с): промах и так стоит игроку времени — барабан продолжает крутиться, и цифру приходится ловить заново. Вторая санкция была двойным наказанием, поэтому `MISS_PENALTY_MS` удалён и с клиента, и с сервера
   - Клиент без `taps` (старая версия) по-прежнему работает: считается только время клиента, ограниченное серверными часами
   - Результат сдаётся один раз: повторный `POST /api/safe/crack` не перезаписывает уже засчитанное время (возвращает `already_recorded`), поэтому возврат на экран взлома не ухудшает и не «перезапускает» игру
   - `/api/safe/current` отдаёт `crack_window_ms`, `crack_remaining_ms` (обратный отсчёт) и `pending_cracks` (сколько участников ещё не сдали → «Ждём остальных»), а также `collecting_safe` + `my_collecting_deposit` — сейф, который принимает вклады прямо сейчас (во время взлома это уже сейф следующего дня: его банк, участники и отсчёт до следующего взлома)
   - После закрытия окна сервер принимает результат ещё 5 секунд (`CRACK_GRACE_MS`) — допуск на доставку того, что игрок отправил до дедлайна; клиенту этот запас не показывается
5. **Итоги подводятся сразу, как только результат сдали ВСЕ участники** (обычно через 5–20 секунд), — ждать конца окна не нужно. Если кто-то ушёл от компьютера, взлом закрывается по дедлайну, а не сдавшему достаётся «техническое поражение»: `crack_time_ms = NULL` → «не успел», приз 0 (`finalizeCracking()` → `calculateSafeWinners()`; таймер ставит `startCracking()`, досрочно итоги вызывает `submitCrackTime()`, каждую минуту cron зовёт `finalizeCrackIfDue()` как страховку после рестарта, а при старте процесса — `resumeCracking()`):
   - Депозиты сортируются по `crack_time_ms ASC NULLS LAST` (быстрее всего → первые, не сдавшие → в конце)
   - Идём по списку и выплачиваем `amount × 1.5` пока хватает `prize_pool`
   - Следующему за ним достаётся **остаток пула** (частичный приз), всем остальным — 0
   - Так как пул = 90% банка, а выплата ×1.5, денег хватает примерно на 60% вкладов: полный ×1.5 получают самые быстрые, поэтому порядок по времени решает всё
   - Клиент показывает **фактический приз из БД** (`my_deposit.prize`), а не прогноз «вклад × 1.5», и отдельно — результат **«чистыми»** (`prize − amount`): приз является выплатой, а не заработком, поэтому «+$37.50» при вкладе $25 показывается как «Приз $37.50 · чистыми +$12.50». Исходов пять (`outcomeOf()` в `Safe.tsx`):
     - `prize > amount` → **🏆 ПОБЕДА** (зелёный) — полный приз ×1.5, прибыль;
     - `prize = amount` → **⚖️ В НОЛЬ** (голубой) — остатка пула хватило ровно на возврат вклада;
     - `0 < prize < amount` → **⚠️ ЧАСТИЧНЫЙ ПРИЗ** (янтарный) — пул закончился, игрок в минусе, и называть это победой нельзя;
     - `prize = 0` при сданном времени → **❌ ПОРАЖЕНИЕ** (красный) — пул разобрали более быстрые;
     - `crack_time_ms = NULL` → **⏱ НЕ УСПЕЛИ** (красный) — техническое поражение.
     Те же статусы и «чистыми» показываются по каждой строке списка результатов; счётчик `winners_count` (все, кто получил выплату, включая частичную) в интерфейсе подписан «С призом», а не «Победителей»

**Экран `/safe` — три блока, ничего лишнего:**
1. **Взлом** (только пока идёт): остаток окна, сколько участников не сдали, кнопка «🔓 СОБРАТЬ КОД» / «👀 СМОТРЕТЬ ВЗЛОМ» либо «✅ результат засчитан».
2. **Сбор** — главный блок: крупный таймер до взлома (`.timer`), банк, призовой пул, участники, свой вклад с возвратом и форма вклада. Работает всегда, в том числе во время взлома предыдущего раунда.
3. **Последний раунд** — единственная история, которую показывает экран (`last_finished` + `my_last_deposit` из `/api/safe/current`, весь список раундов остаётся в БД): сводная строка, а внутри — исход игрока и таблица результатов. Раскрывается автоматически только один раз и **только участнику раунда** (`my_last_deposit != null`): тому, кто в этом раунде не вкладывался, чужие результаты сами не раскрываются — строка раунда остаётся, кнопка «ИТОГИ» по желанию. После просмотра ставится ключ `vault:safe-result-seen:<id>` (при уходе со страницы или по кнопке «СВЕРНУТЬ» в шапке блока — отдельной кнопки «✓ Я ПОСМОТРЕЛ» нет, одной достаточно), и дальше раунд показывается свёрнутой строкой, а не висит на первом месте.

Автопереход в мини-игру во время взлома тоже делается один раз на раунд (ключ `vault:safe-crack-visited:<id>`): раньше игрока выдёргивало на `/safe/crack` при каждом заходе, и он не мог ни вернуться, ни внести вклад в следующий сейф. Переход происходит **только в видимой вкладке** (`document.visibilityState === 'visible'`): в фоне `requestAnimationFrame` остановлен, а серверные секунды идут — открыв игру «в никуда», игрок потерял бы раунд, даже не увидев его. Вернулся во вкладку позже — переход сработает в этот момент (за это отвечает `visibilitychange` в редиректоре).

**Игрока выдёргивает во взлом с любого экрана.** Вклад в сейф сделан заранее, окно взлома короткое (по умолчанию 60 с), поэтому когда таймер сбора истекает, игрок должен оказаться в мини-игре, где бы он ни был: в главном меню, в `/rocket`, в `/duel`, в профиле. Промежуточного экрана с кнопкой «🔓 СОБРАТЬ КОД» на пути быть не должно. Переход делает `SafeCrackRedirector` (`components/safe/SafeCrackRedirector.tsx`), смонтированный в `App.tsx` рядом с роутами (не привязан к экрану сейфа, от онбординга не зависит). Локальный автопереход из `Safe.tsx` удалён — источник перехода один.

Триггеры: socket-событие `safe_crack_started` (мгновенно), **адаптивный опрос** `/api/safe/current` — раз в 10 с в спокойное время и раз в 1.5 с, когда взлом идёт или до него меньше двух минут, возврат вкладки в видимое состояние и смена экрана. Опрос — не дублирование сокета, а страховка: событие теряется при переподключении и после сна телефона, а терять раунд из-за этого нельзя. Запрос один на проверку, флаг «в полёте» с 8-секундным watchdog, поэтому зависший `fetch` не блокирует переход до конца сессии.

Условия перехода: сейф в статусе `cracking`, у игрока есть вклад в ЭТОМ раунде (`my_deposit`), результат ещё не сдан, до конца окна больше 3 с, и в этой вкладке раунд ещё не открывали (`vault:safe-crack-visited:<id>` в `sessionStorage` — иначе игрока, который сам вышел из мини-игры, чтобы внести вклад в следующий сейф, дёргало бы обратно бесконечно). В фоновой вкладке не переходим: там `requestAnimationFrame` остановлен, а серверные секунды идут. Переход делается `push`, поэтому «назад» возвращает туда, откуда забрали. Каждая ветка решения логируется в консоль как `[safe-crack] …` — если перехода нет, по F12 сразу видно почему (нет вклада / уже сдал / раунд уже открывали / окно закрывается / вкладка в фоне).

**Что происходит с партией, из которой выдёргивают.**

- **Ракета — останавливаем за игрока.** Перед уходом редиректор отправляет `cashout` по активному раунду: кэшаут на текущем множителе возвращает `bet × mult`, то есть при x1.00 ровно ставку и дальше только больше — игрок не теряет ничего. Ждать конца полёта нельзя: при кривой `exp(0.075·t)` полёт до x10 длится ~31 с, до x50 ~52 с, то есть дольше всего окна взлома. Команда уходит после `nav()`, когда экран ракеты уже размонтирован, — результат обрабатывает `RocketFlightBadge`, двойной обработки нет. Сам раунд от клиента не зависит: `startRocketRound` тикает каждые 50 мс и сам гасит раунд через `processCrash` (`profit = -bet`), поэтому «зависших» полётов не бывает. `rocket:launch` отправляется `setTimeout`, который переживает размонтирование экрана: даже если игрока увели в эти 100 мс, тики стартуют.
- **`RocketFlightBadge`** (`components/common/RocketFlightBadge.tsx`) — плашка «🚀 x2.40 · в полёте · ЗАБРАТЬ» на любом экране, кроме `/rocket`: если игрок ушёл с экрана ракеты сам (меню, «назад»), ставка не сгорает. Сокет в приложении один и из комнаты раунда не выходит, поэтому `tick`/`crash`/`cashout_result` продолжают приходить после размонтирования `Rocket.tsx`. Бейдж сам обновляет баланс, сам делает автовклад в сейф (`auto_safe_percent`) и сам сообщает о падении. Кто обрабатывает события раунда, определяет флаг `isRocketScreenActive()` (а не текущий путь: в момент перехода путь уже новый, а обработчик ещё старый). `useHasRocketFlight()` ре-рендерит только на старт/конец раунда, не 20 раз в секунду, и добавляет в мини-игре запас прокрутки 72 px, чтобы плашка не накрыла барабаны.
- **Возврат на `/rocket` во время полёта** восстанавливает раунд из `utils/rocketFlight.ts` (фаза `flying`, `roundId`, множитель, повторный `rocket:join`) — игрок видит свой полёт и штатный кэшаут, а не форму ставки.
- **Дуэль — анимацию можно сбивать.** Исход и деньги посчитаны сервером ещё в `acceptDuel`, экран `/duel/:id` только крутит монету 2.8 с. Результат не теряется: он в БД, в истории дуэлей и в уведомлениях (в дуэлях уже есть реплеи, общая система реплеев планируется). Лобби `/duel` тоже безопасно — вызов живёт на сервере.
- **Остальные экраны** (главная, вклад, депозит, вывод, профиль, админка) серверных операций, зависящих от присутствия экрана, не имеют.
- **Итоги сейфа ничего не перезаписывают в чужих играх:** `finalizeCracking` трогает только `safes`/`safe_deposits` своего раунда и баланс через `modifyBalance`; раунды ракеты и дуэли живут в своих таблицах и своих циклах событий.

**Экран `/safe` во время взлома** показывает короткую строку состояния (сейф, остаток окна, «сдали результат: X из Y», статус своего вклада), а не отдельное «меню взлома»: игрок с вкладом сюда просто не попадает — его уводит редиректор. Кнопка «🔓 СОБРАТЬ КОД» оставлена только как запасной вход для того, кто вышел из мини-игры сам, плюс «👀 СМОТРЕТЬ ВЗЛОМ» для тех, кто в раунде не участвовал. На главной в это же время написано, участвует ли игрок в идущем взломе («вы участвуете в этом раунде — мини-игра откроется сама» / «вы не вносили вклад в этот раунд — взлом идёт без вас»), чтобы причина перехода (или его отсутствия) была видна без консоли.

**Подпись отсчёта — часами, а не «время МСК».** `/api/safe/current` отдаёт `crack_at_msk` («21:00», из `safe_crack_hour`/`safe_crack_minute` через `fmtMSK(nextMSK(...))`), и под таймером написано «взлом в 21:00 МСК» (на главной — «СЕЙФ #2 · взлом в 21:00 МСК»). Обратный отсчёт остаётся, но игрок видит конкретное время: «до взлома (время МСК)» не отвечало на вопрос «во сколько» на вопрос «во сколько».

Оба флага живут в **`sessionStorage`** (`tabStore` в `Safe.tsx`), а не в `localStorage`: он свой для каждой вкладки. С общим хранилищем две вкладки одного браузера делили флаг — в одной мини-игра открывалась сама, в другой нужно было жать кнопку и терять секунды, а итоги в одной раскрывались, в другой нет.

**Чей аккаунт открыт — видно на экране.** `/safe` показывает `👤 @username · баланс $X`, `/safe/crack` — `👤 играет @username`. При тестировании с несколькими браузерами и аккаунтами это единственное место, где сразу видно, чей вклад и чей результат засчитывается.

**Опрос `/api/safe/current`:** экран сейфа — раз в 10 с, главная — раз в 20 с, остальное приходит по socket (`safe_deposit`, `safe_crack_started`, `safe_finished`, `safe_cancelled`, `safe_created`). Результаты раунда запрашиваются один раз на раунд, а не на каждом опросе.
   - Ручного управления взломом в админ-панели нет: ни «запустить взлом», ни «подвести итоги» (эндпоинты `/api/admin/start-cracking` и `/api/admin/finalize-cracking` удалены). Всё делает сервис по расписанию, досрочной финализацией и cron-страховкой

**Защита от ботов** (в production, не демо):
- Скорости барабанов рандомизируются ежедневно и приходят с сервера (`drum_speeds` в `/api/safe/current`) — клиент использует именно их и для отрисовки цифр, и для проверки попадания, фиксируя значения на момент старта вращения
- Код показывается **один раз** — за 3 секунды до старта вращения, крупно; во время игры над барабанами нет ни кода, ни «цель: X» для каждого барабана, игрок взламывает сейф по памяти
- Предстартовая церемония (3-2-1 → код 3 с → вращение) **сокращается до 0.1 с + код 1.4 с**, если игрок пришёл, когда до конца окна осталось меньше 12 с (`firstRemaining` из первого ответа `/api/safe/current`). Игрока теперь выдёргивает в мини-игру с любого экрана, и при позднем приходе полная церемония съедала бы всё окно до старта вращения. Если сервер молчит 1.5 с, играется обычная схема — на цифре «3» никого не держим
- Любой заход в мини-игру (кнопкой или автоматически) ставит флаг `vault:safe-crack-visited:<id>`, поэтому повторно в этом раунде вкладку не выдёргивает
- Время засчитывается как `max(заявленное клиентом, пересчитанное сервером по тапам, серверное время от crack_started_at)`, поэтому «нарисовать» себе быстрые миллисекунды нельзя; ввод после закрытия окна отклоняется
- Цифры кода проверяются на сервере по присланным моментам тапов: несовпавший тап = отклонённый результат (400), а барабан в клиенте останавливается только на правильной цифре
- Время <500мс = подозрительно (бот)

### 5.4 Vault Вклад 💎

Множители: `{1: 1.0, 7: 1.3, 14: 1.6, 30: 2.0}`

**Блокировка:**
- Проверяется мин. $10, макс. = `vault_max_deposit`
- Средства замораживаются (frozen_balance += amount)
- Создаётся запись `vault_deposits` со статусом `active`

**Ежесуточное распределение в 00:00 (`dailyVaultDistribution()`):**
1. Берётся `revenue` — сумма ВСЕХ записей `daily_revenue` за вчера (это УЖЕ чистый доход после выплаты рефералов)
2. Автопул = revenue × 15% (`vault_pool_percent`)
3. Ручной пул = `manual_pool_addition` (из настроек, добавленное админом за день)
4. Обнуляем `manual_pool_addition` после снятия
5. Суммарный пул = auto + manual
6. Для каждого активного вклада считаем вес: `weight = amount × multiplier`
7. Суммарный вес `totalWeight = sum(weight)`
8. Каждый вклад получает: `daily_profit = pool × weight / totalWeight`
9. `days_elapsed += 1`
10. Если срок истёк (`days_elapsed >= term_days`):
    - Выплачиваем `amount + accumulated_profit` на баланс
    - Размораживаем тело
    - Ставим статус `completed`
11. Пересчитываем новый `vault_max_deposit = roundDownClean(max(pool × 10, 100))`
12. Сохраняем статистику дня в `vault_pool_daily` (базовая ставка = pool/total_locked)

**Досрочный выход:**
- Доступен только для сроков > 1 дня
- Тело возвращается на баланс (размораживается)
- `accumulated_profit` не выплачивается (сгорает)
- Статус становится `early_unlock`

## 6. Cron-задачи

| Время (UTC, сервер) | Задача | Файл/функция |
|--------------------|--------|-------------|
| `0 6 * * *` (09:00 МСК) | Создать дневной Сейф (с проверкой бонус-режима) | `cron` → `services/safe.createDailySafe()` |
| `* * * * *` (каждую минуту) | Старт взлома в настроенное время МСК (`safe_crack_hour`/`safe_crack_minute`, в т.ч. догоняюще после простоя) + страховка закрытия истёкшего окна взлома | `cron` → `services/safe.startCracking()` / `finalizeCrackIfDue()` |
| по таймеру окна взлома | Подвести итоги Сейфа, распределить призы ×1.5 по скорости | `services/safe.finalizeCracking()` → `calculateSafeWinners()` |
| при старте процесса | Восстановить таймер незавершённого взлома после рестарта | `services/safe.resumeCracking()` |
| `0 0 * * *` (00:00) | Дневное распределение Вклада, выплаты истёкших вкладов, пересчёт макс. вклада | `cron/vault-deposit.dailyVaultDistribution()` |

> ⚠️ В продакшене часовой пояс сервера нужно настроить на Europe/Moscow (UTC+3) или считать время относительно пользовательского часового пояса. В MVP используется системное время сервера.

## 7. Безопасность

1. **PIN-код вывода** — 4 цифры, хранится как bcrypt-хеш, никогда не возвращается клиенту.
2. **JWT** — подписывается секретом из конфига (`jwtSecret`), срок жизни 30 дней.
3. **Авторизация middleware** — на каждый эндпоинт проверяется `Authorization` заголовок, в запрос подставляется объект пользователя `req.user`.
4. **Админ-доступ** — отдельный middleware `adminOnly`, проверяющий что `telegram_id` пользователя входит в `ADMIN_TELEGRAM_IDS` из переменных окружения.
5. **Денежные операции идут в SQL-транзакциях** (`BEGIN/COMMIT/ROLLBACK`) — см. `modifyBalance()`. Это гарантирует, что баланс и запись в `transactions` обновятся одновременно.
6. **Демо-режим** флаг `DEMO_MODE=true` отключает реальные TON-операции и позволяет вход по `demo:<id>:<username>`, что должно быть отключено в проде.

Что нужно добавить в проде (помечено TODO):
- Проверка подписи Telegram initData по алгоритму HMAC-SHA256 с bot_token
- Rate-limiting (настройки для каждого эндпоинта указаны в ТЗ: rocket_start 10/мин, withdraw 3/час, общее 60/мин)
- ~~Серверный замер времени взлома Сейфа (а не client-side)~~ — сделано: `crack_started_at` + `max(client, server)` в `submitCrackTime()`
- Детекция мультиаккаунтов: один TON-адрес вывода = один аккаунт
- Хранение JWT-секрета не в коде, а в переменной окружения

## 8. 3D-сцены (Three.js)

Все 3D-модели **процедурные** — собираются из примитивов (Box, Sphere, Cylinder, Cone, Torus) на старте приложения и не требуют загрузки внешних GLTF-файлов. Это сделано для минимального размера бандла и быстрой загрузки.

| Сцена | Компонент | Что происходит |
|-------|-----------|----------------|
| Сейф (онбординг/главная) | `three/main/VaultScene.tsx` | Сейф слегка вращается и покачивается, вокруг кружатся золотые монеты, имитируя дождь |
| Ракета | `three/rocket/RocketScene.tsx` | Стадия idle: ракета покачивается на старте. Flying: огонь, взлёт, тряска при x>3, звёзды крутятся, камера отъезжает с набором высоты. Win: призрак-ракета летит дальше. Lose: ракета скрывается, разлетаются 20 обломков. |
| Дуэль | `three/duel/DuelScene.tsx` | Арена в фиолетовом свете, два постамента. В idle монета вращается на месте. При flippling монета подлетает по параболе, вращается с траекторной скоростью и падает. |
| Сейф (взлом) | `three/safe/SafeCrackScene.tsx` | Красная мигающая подсветка, три барабана на дверях сейфа, красные стрелки-индикаторы сверху. В стадии spinning барабаны крутятся с各自 скоростью. |

## 10. Поток запуска приложения (на примере Ракеты)

1. Игрок открывает `/rocket`, видит ставку $10 → нажимает «🚀 ЗАПУСТИТЬ»
2. Фронт → `POST /api/rocket/start {bet:10}`
3. Бэкенд в `services/rocket.placeBet()`:
   - Проверяет лимиты (мин $1, доступный баланс, max_bet по кассе)
   - Списывает $10 с баланса через `modifyBalance()` (пишет транзакцию)
   - Распределяет комиссию ($9 в кассу, $0.30 рефоводу, $0.70 в доход платформы)
   - Генерирует `crash_at` по алгоритму
   - Создаёт `rocket_rounds` запись
   - Возвращает `{ round_id, crash_at, max_bet }`
4. Фронт переключает сцену в режим «flying», отображает 3D ракету
5. Фронт подключается к `/rocket` namespace Socket.io и отправляет `rocket:join` и `rocket:launch`
6. Сервер в `websocket/rocket.startRocketRound()` запускает setInterval 20 FPS:
   - Рассчитывает `mult = e^(0.075 * elapsed)`
   - Шлёт `tick` в комнату раунда
   - При достижении `mult >= crashAt` — вызывает `processCrash()`, шлёт `crash`
7. Игрок нажимает «💰 ЗАБРАТЬ»:
   - Фронт шлёт `cashout {elapsed}` (доверительный, но сервер перепроверяет по своему времени)
   - Сервер в `processCashout()` проверяет что текущий mult < crashAt
   - Выплачивает gross_win = bet × mult через modifyBalance
   - Снимает gross_win из кассы Ракеты
   - С 3% шансом подменяет crash_at на «красивый» (20-80)
   - Возвращает результат
   - Шлёт окончательный `crash` с финальной точкой
8. Фронт показывает экран результата (выигрыш или проигрыш), догружает историю

## 11. Масштабирование и дальнейшая разработка

### Куда добавлять новую игру (рецепт)
1. Добавьте таблицу в `db/init.sql` (например, `mines_rounds`)
2. Создайте сервис в `services/mines.ts` с функциями placeBet, reveal, cashout — используйте `modifyBalance()` и `logPlatformRevenue()` для учёта комиссии
3. Добавьте REST routes в `api/routes/mines.ts` и зарегистрируйте в `index.ts`
4. Если нужен реалтайм — создайте websocket-обработчик в `websocket/mines.ts` и зарегистрируйте в `index.ts`
5. Добавьте cron-задачи если игра имеет периодическую логику
6. Добавьте экраны в `components/mines/` и Three.js сцену в `three/mines/`
7. Добавьте плитку игры на главный экран `components/layout/Home.tsx`
8. Добавьте роут в `App.tsx`

### Куда править комиссии и лимиты
Все правки — **только через админ-панель** или напрямую в таблице `settings`. Никогда не хардкодьте цифры в сервисах; всегда читайте через `getSetting()`.

### Добавление нового уведомления
Используйте `notify(userId, message, data)` из `services/notifications.ts` — оно автоматически дойдёт до подключённого сокета пользователя как событие `notification`. Для Telegram-уведомлений в проде расширьте эту функцию вызовом `bot.telegram.sendMessage(userId, message)`.
