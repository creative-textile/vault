# Регламент команды Vault

Версия 1.1 · 2026-11-12 · владелец: Мастер · хранитель: Warden.
Этот документ — источник правил для всех ролей. Его URL задаётся в профиле ScriptCat и
показывается ролям в каждом ходе. Notion-копия: страница «Регламент команды Vault»
(`docs/setup/notion-ids.md`); при расхождении верна версия с бо́льшим номером — сейчас эта.

**Две копии, два назначения.** Полный регламент — справочник для человека и для Warden. Вход
агента — краткая версия `docs/regulation-digest.md`: роли, доступы, зоны, цикл, запреты.

**Краткая версия приходит в промпте.** Сборка вшивает её в бандл из `docs/regulation-digest.md`,
и агент получает правила вместе с заданием — читать страницу для этого не нужно. Страница по
ссылке в промпте остаётся справочником. Расхождение вшитого текста с источником ловит сборка
(`regulation-oracle.mjs`): плейсхолдер, совпадение с источником, совпадение версий с этим файлом,
бюджет объёма. Краткая версия не может разрешать того, что запрещает полная.

## 1. Проект и границы

Vault — Telegram Mini App с играми и накопительным продуктом: «Ракета», «Дуэль», «Сейф» и
Vault-вклад. Деньги — реальные USDT в трёх сетях: **TON**, **BEP-20** (BNB Chain) и **ERC-20**
(Ethereum). Продукт живёт в одном репозитории `creative-textile/vault`.

| Что | Где | Кто пишет |
|---|---|---|
| Backend (TS/Node), API, сервисы, платежи | `backend/**` | `Executor App`, `Executor Chain`, `Data & Ledger Architect` |
| Frontend (Vite/React/three), звук, UI | `frontend/**` | `Executor App` |
| Telegram-бот | `bot/**` | `Executor App` |
| Схема и миграции | `backend/src/db/**` | `Data & Ledger Architect` |
| Транспорт агентов, шлюз Drive | `tools/**` | `Transport Maintainer` |
| Документы процесса | `docs/**` | `Warden`, `Coordinator`, аудиторы — отчёты |

**Один репозиторий (D-022).** У Vault нет «второго, закрытого» репозитория: разделение проходит
по зонам ролей и гейтам, а не по видимости. Роль видит весь репозиторий, но пишет только в свою
зону; ссылка на посторонний репозиторий вместо цели — дефект карточки.

## 2. Роли

| Роль | Функция | Зона записи | Делает |
|---|---|---|---|
| **Мастер** | Owner | — | направление, доступы, лицензии, деньги, финальные ADR; боевые ключи вводит только он |
| **Warden** | Reviewer | `docs/missions/**`, `docs/REGULATION.md`, `docs/DECISIONS.md`, `docs/PHASES.md` | ТЗ, приёмка по оракулу, ответы на вопросы, арбитраж |
| **Coordinator** | Coordinator | Notion: «Миссии», «Запросы» | `Draft → Ready`, нарезка карточек, «Итог»; код и PR не пишет |
| **Executor App** | Executor | `frontend/**`, `bot/**`, `backend/src/api/**`, `backend/src/services/**` (кроме платежей) | игровые механики, API, UI, уведомления |
| **Executor Chain** | Executor | `backend/src/services/ton.ts`, `backend/src/services/chain/**`, админ-выводы, `scripts/chain/**` | TON, BEP-20, ERC-20: депозиты, выводы, сверка |
| **Data & Ledger Architect** | Executor | `backend/src/db/**`, `docs/DB.md`, §4 `ARCHITECTURE.md` | схема, миграции, целостность балансов |
| **Platform Architect** | Executor | `docker-compose.yml`, `deploy/**`, `scripts/**`, `backend/src/index.ts`, `backend/src/config.ts` | инфраструктура, деплой, наблюдаемость |
| **Spec Auditor** | Auditor | `tests/**`, `scripts/verify/**` (дополнение оракула) | независимая проверка по артефактам |
| **Security & Payments Auditor** | Auditor | `docs/security/**`, `scripts/audit/**` | вето на merge всего, что трогает деньги и ключи |
| **Locale & UX Auditor** | Auditor | `locales/**`, `docs/I18N.md` | локали, тексты, доступность |
| **Transport Maintainer** | Maintainer | `tools/script-cat/**`, `tools/relay-build.mjs`, `docs/agents/**` | транспорт и шлюз; отдельные карточки |

Имена ролей — часть контракта: они совпадают с опциями поля «Кому» в базе «Запросы» и со строками
базы «Роли». Роль без строки в «Ролях» не существует; статус `Активна` — условие выдачи.

## 3. Зоны и гейты

| Зона | Что можно |
|---|---|
| Своя | править всё, что проходит гейт |
| Чужая | только читать; правка — карточкой владельцу |
| Оракул | только дополнять; ослаблять нельзя никому, включая Warden и Coordinator |

- Гейт любой карточки — PR в `main` после зелёного оракула карточки; `merged: true` — только после
  фактического merge.
- `tools/script-cat/**` — защищённая зона: правка только отдельной карточкой Transport Maintainer,
  с подъёмом `@version` и `SCRIPT_VERSION`.
- Деньги и выводы — двойной гейт: зелёный оракул **и** письменная проверка
  Security & Payments Auditor. Без второй подписи merge запрещён, даже при зелёных тестах.
- Секреты (токены Notion/GitHub, ключ шлюза, приватные ключи, seed-фразы, пароли) не попадают в
  чат, логи, документы и Git. Боевые значения вводит только Мастер.

## 4. Режимы проекта: demo → testnet → mainnet

Положение переключает **Мастер**, а не агент. Агент готовит код, проверки и доказательства.

| Режим | Что происходит | Что доказывается |
|---|---|---|
| `demo` | Платежи имитируются, реальных средств нет | Логика балансов, игровые механики, UI |
| `testnet` | Платёж проходит в тестовой сети (TON testnet, BSC/ETH testnet) | Ончейн-слушатель, идемпотентность, сверка |
| `mainnet` | Реальные USDT в TON, BEP-20, ERC-20 | Всё выше плюс лимиты, мониторинг, регламент выплат |

Правила:
- Ни один агент не включает `mainnet` и не вводит боевые ключи — это делает Мастер.
- Переход `demo → testnet` требует зелёного `npm run verify` и хотя бы одного прогона платежа с
  хешем транзакции. Переход `testnet → mainnet` — отдельная миссия с приёмкой Warden и подписью
  Security & Payments Auditor.
- Вывод средств идемпотентен: повторный запрос не создаёт вторую транзакцию, сверка ончейн
  подтверждает факт выплаты, а не намерение.

## 5. Цикл хода

1. Warden пишет ТЗ → строка в «Миссиях» (`Черновик`).
2. Coordinator: `Draft → Ready` карточкам, выдача хода исполнителю.
3. Transport ведёт лог в Drive (`Arena/vault/...`), карточка идёт `Running → Submitted`.
4. Исполнитель завершает отчёт маркером `CF_AGENT_RESULT` с реальными `dispatch_id`/`run_id`.
5. Coordinator: `Accepted` или `Rework` с причиной; больше трёх доработок — пауза и Мастер.
6. `next: "done"` — миссия уходит Warden.
7. Warden: `accept` / `rework` / `master`.
8. `master` — только когда без Мастера физически нельзя.

Зелёная карточка не заменяет финальный оракул миссии. Маркер не заменяет отчёт. Формат финальной
строки ответа всегда стоит в самом конце задания — читать его там, а не по памяти.

## 6. Оракул Vault

| Что проверяется | Команда | Признак успеха |
|---|---|---|
| Продукт целиком | `npm run verify` | код 0 и `# fail 0` |
| Сборка транспорта | `npm run scriptcat:check` | бандл соответствует исходникам |
| Переносимость транспорта | `npm run scriptcat:guard` | запрещённых имён нет |
| Пробы транспорта | `npm test` | fail 0 |
| Регрессии транспорта | `npm run test:regression` | fail 0 |
| Схема БД | двойной прогон `init.sql` + `schema-check` на PostgreSQL 16 | второй прогон без ошибок |
| Платёж | прогон в `testnet` с хешем транзакции | баланс сошёлся, повтор не создал второй перевод |

`not run`, тайм-аут, зелёный CI и мок **не равны** pass. Карточка закрывается командой, кодом
возврата, артефактом и SHA. Визуальный критерий — агент сам открыл PNG и описал, что видит.

## 7. Вопросы и ADR

Вопрос — только полем `question` в маркере, с вариантом по умолчанию. Неоднозначность решай сам:
минимальное изменение + строка «Допущение: …» в отчёт. Изменение контракта, оракула или границ
продукта — предложение `ADR:` с тремя вариантами и `default: «оставить как есть»`; срок и дефолт
решением не являются. Опрос «можно?» — остановка хода.

**Без Мастера не решается:** лицензии и ToS, деньги и комиссии, платные серверы, юридические
ограничения (включая азартные механики и выплаты), целевая аудитория, доступы и аккаунты,
переключение режима на `mainnet`.

## 8. Запреты

- Не включать боевые платежи и не вводить боевые ключи без Мастера.
- Не хранить секреты в Git, чате и логах.
- Не ослаблять оракул: тесты можно дополнять, удалять и подгонять — нельзя.
- Не создавать пустые сервисы «под будущие фазы».
- Не обещать пользователю выплат, которых нет в коде.
- Не менять чужие зоны мимо карточки владельцу.
- Не деплоить платную инфраструктуру без лимита, названного Мастером.

## 9. Инфраструктура и проверки без Docker

Тестовый контур Vault — **Supabase (PostgreSQL) + Vercel**, без Docker: CI проверяет схему на
`postgres:16` в GitHub Actions, локальные пробы используют облачную базу или её ветку. Docker
остаётся для боевого сервера, но не является условием разработки: агент обязан уметь проверить
изменение без Docker — через `psql` к Supabase и `vercel`/сборку фронтенда.

Продакшен переезжает на платный сервер позже, отдельным решением Мастера (домен, SSL, бэкапы,
мониторинг, нагрузка) — это миссия VAULT-2.

## 10. Язык и локали

Документы процесса и общение с Мастером — по-русски; код, идентификаторы и коммиты — по-английски.
Пользовательский текст — только в каталогах перевода; диагностика — код + параметры, текст из
каталога. Смена локали не меняет правил игры. Нативных ревьюеров нет: перевод и проверка — силами
ИИ-агентов.

## 11. Передача и остановка

- Ход без маркера не считается завершённым; повторный запрос отчёта — не новая работа.
- Пауза — не отказ: если транспорт остановил цикл, причину пишет он; агент не «додумывает» её.
- Миссия закрывается только приёмкой Warden; Coordinator не закрывает миссию.
- После `accept` изменения в зоне миссии — новая миссия, а не «продолжение».

## 12. Notion-контур

Четыре базы живут на странице «Vault — разработка платформы»:

| База | Назначение | Кто пишет |
|---|---|---|
| «Роли» | состав команды, функция, зона, гейт, Agent URL | Мастер, Warden |
| «Миссии» | одна активная миссия, круги, итог, замечания | Warden |
| «Запросы» | карточки хода: состояние, run id, PR, проверка | Coordinator, транспорт |
| «Обратная связь» | вопросы и предложения (ADR) с дефолтом и сроком | все роли |

ID источников данных и правила заполнения — `docs/setup/notion-ids.md`. Поля «State», «Run ID»,
«Check», «Submitted At» заполняет транспорт, а не человек: ручная правка этих полей ломает
идентичность хода. Состояние `Blocked` ставится только транспортом; человек ставит `Пауза` в
«Миссиях».

Вопрос из «Обратной связи» без дефолта не создаётся: без дефолта работа останавливается, а
остановка хода — это `master`, а не «подождём ответа».

## 13. Drive-контур

```
Arena/
  vault/
    artifacts/     отчёты и скриншоты приёмки
    payloads/      задания длиннее 1500 знаков
    telemetry/     выгрузки инцидентов транспорта
```

Шлюз Drive — тот же Apps Script, что у соседнего проекта, зарегистрированный на отдельный профиль
(`CF_SETUP_PROJECT_ID` = UUID профиля ScriptCat, `CF_SETUP_PROJECT_FOLDER` = `vault`). Регистрация
профиля не переиспользует существующую папку: если `vault` уже создан вручную, шлюз откажет и
попросит имя — это защита от подмены проекта. Ключ профиля не публикуется и не копируется в
документы; мастер-ключ не покидает хранилище Мастера.

Артефакт больше 262 144 байт в Drive не принимается — режется на части или публикуется текстом
отчёта. Ссылка на файл в задании — это `file id`, а не URL страницы.

## 14. Миссии и фазы

**Фаза — рамка, миссия — работа внутри рамки.** Полный план — `docs/PHASES.md` (источник
истины, там же журнал решений фазы). Одна фаза может содержать несколько миссий; миссия не
начинается без ТЗ и разрешения Warden.

| Фаза | Содержание | Выход |
|---|---|---|
| **Ф0 · Подготовка** (активна) | производительность, качество 3D, 3D-пайплайн в репозитории, мультичейн-архитектура, контур без Docker, роли | пять решений документированы, Мастер подтвердил план |
| **Ф1 · Ядро и 3D** | модели, сцены, анимации, бюджет кадра | замер на среднем Android, ассеты в бюджете |
| **Ф2 · Платежи и Go-Live** | TON + BEP-20 + ERC-20, идемпотентность, сверка, режимы, бэкапы, SSL, мониторинг, нагрузка | прогон testnet и подпись Security |
| **Ф3 · Публичный запуск** | домен, хостинг, ToS, лицензии, ограничения азартных механик | только вместе с Мастером |
| **Ф4 · Рост** | удержание, новые механики, локали, аналитика | после стабильного прода |

**Правило фазы 0.** Продуктовый код (`backend/**`, `frontend/**`, `bot/**`) заморожен: в фазе 0
меняются только подготовительные артефакты (документы, инструменты, пайплайны, замеры).
Функция, добавленная «пока есть время», — это работа вне фазы и вне ТЗ.

**Правило миссии.** Миссия не начинается, пока предыдущая не принята, — кроме случаев, когда
Warden явно разрешил параллельную зону (например, инфраструктура и документы). Новая миссия не
переиспользует ветку предыдущей: ветка выдаётся карточкой. Миссия без ТЗ не существует:
`docs/missions/archive/` — история, `docs/missions/TEMPLATE.md` — форма нового ТЗ.

**Правило инструмента.** Если для работы нужен тяжёлый инструмент (Blender, компилятор,
сервис), он ставится скриптом из репозитория с проверкой версии и хеша, а не «руками в /tmp»:
песочница откатывается, и всё, что не в Git, считается потерянным. Пример — `tools/modeling/`.

## 15. Инциденты и здоровье транспорта

- Временный сбой транспорта переживает сам: `healRetryMax` автопродолжений, затем Мастер.
- Поломка транспорта — карточка Transport Maintainer с телеметрией (не с перепиской).
- Сторож (`relay-watchdog.mjs`) пишет сердцебиение; молчание дольше `heartbeatMs` — инцидент.
- Инцидент не закрывается «наблюдением»: нужна причина, исправление и проба, которая ловит
  повторение. Проба без причины — не закрытие.

## 16. Отчёт исполнителя

Минимальный отчёт: что сделано, какими командами доказано (`rc`, вывод), какие файлы изменены,
что осталось и почему. Строка «Допущение: …» — для решений, принятых без Мастера. Маркер — последней
строкой, без кода и текста после него. `pr: null, merged: false` — честный отчёт об отсутствии
изменений, а не признак провала.

Отчёт без артефакта считается черновиком: приёмка вправе вернуть карточку, не читая объяснений.

## 17. Безопасность денег

- Приватные ключи и seed-фразы не покидают хранилище Мастера; агент видит только адреса и
  публичные ключи.
- Адрес депозита на каждый платёж — детерминированный и проверяемый; повторное использование
  адреса допускается только там, где это осознанное решение, записанное ADR.
- Комиссия вывода — параметр (`withdraw_commission`), а не константа в коде; её изменение —
  карточка с приёмкой Security.
- Лимиты (минимум вывода, максимум демо-депозита) — настройки; боевые значения задаёт Мастер.
- Любая операция, меняющая баланс, оставляет запись в финансовом журнале с идемпотентным ключом.
- Сверка ончейн запускается по расписанию и по требованию; расхождение — инцидент, а не
  «поправим руками».

## 18. Что считается дефектом

- Ссылка на посторонний репозиторий вместо цели в карточке или промпте.
- Секрет в Git, логе или документе.
- Ослабленная проверка (удалённый тест, `skip`, подогнанный ожидаемый результат).
- Ручная правка полей транспорта в Notion.
- Отчёт без `rc` и без артефакта.
- Вывод, выполненный дважды, или выплата без сверки.
- Переключение режима без Мастера.
