# Мультичейн USDT: TON + BEP-20 + ERC-20 (архитектура фазы 0)

Версия 0.2 · 2026-11-12 · фаза 0 · автор: Executor Chain · ревью: Security & Payments Auditor.
Статус: порядок сетей **принят Мастером** (TON → BEP-20 → ERC-20); остальное — проект к
утверждению. Код в фазе 0 не меняется. Ключи подписи разобраны отдельно и по-русски:
`docs/security/key-custody.md` (в архитектуре — только техническая ссылка).

## 1. Требование

Мастер: «USDT должен работать на TON, BEP-20 и ERC-20 — не только TON». Сегодня в коде один
сеть — TON, и то как placeholder: `DEMO_DEPOSIT_ADDRESS` один на всех, слушатель депозитов
пустой, вывод — заявка с ручным `tx_hash`. То есть мультичейн — это не «добавить вторую сеть к
рабочему TON», а сразу проектировать три равноценных канала.

## 2. Что общего и что различается

| Свойство | TON (Jetton) | BEP-20 (BNB Chain) | ERC-20 (Ethereum) |
|---|---|---|---|
| Адресация | `UQ…`/`EQ…` (base64url, 48 симв.) | `0x…` (EIP-55) | `0x…` (EIP-55) |
| Единица | jetton USDT (9 dec) | USDT BSC (18 dec) | USDT ETH (6 dec) |
| Комментарий к платежу | `comment` в теле перевода | нет (memo не поддерживается) | нет |
| Подтверждение | ~5 сек | ~3 сек (1 блок) | ~15–60 сек (12 блоков) |
| Финализация | masterchain seqno | N блоков | 12–64 блока |
| Слушатель | `@ton/ton` + TonAPI/Toncenter | `ethers`/`viem` + RPC | `ethers`/`viem` + RPC |
| Стоимость вывода | ~$0.01 | ~$0.05–0.20 | $1–15 (пики) |
| Депозит-адрес | свой кошелёк + memo | отдельный адрес или HD-вывод | отдельный адрес или HD-вывод |

Ключевое различие: **на TON один адрес может обслуживать много пользователей через memo, на
EVM — либо HD-адреса (derivation path), либо один адрес с ручной сверкой**. Это определяет
схему БД и UX.

## 3. Схема данных (проект)

```
wallets                     кошельки пользователя (адрес + сеть), не один на всех
  id, user_id, chain, address, memo, created_at
  UNIQUE(chain, address)             — чужой адрес не привязать
  UNIQUE(user_id, chain)             — по одному адресу на сеть

chain_deposits              входящие, ключ идемпотентности — (chain, tx_hash, index)
  id, user_id, chain, tx_hash, event_index, from_address, amount, confirmations,
  status (seen|confirmed|credited|orphaned), credited_tx_id, created_at

withdrawals                 существующая таблица + сеть
  chain, address, tx_hash, status (pending|broadcast|paid|rejected|failed),
  idempotency_key, broadcast_at, confirmed_at

chain_cursor                докуда прочитан блокчейн (на сеть и на аккаунт)
  chain, cursor, updated_at

chain_reconciliation        ежедневная сверка
  date, chain, onchain_balance, ledger_balance, delta, status
```

Миграции — отдельная миссия фазы 2, в фазе 0 фиксируется только форма.

## 4. Поток депозита

1. Пользователь открывает «Пополнить» → выбирает сеть → получает адрес (+ memo для TON).
2. Слушатель каждой сети читает новые транзакции с `chain_cursor`, пишет в `chain_deposits`
   со статусом `seen`.
3. По достижении `confirmations` — `confirmed`, затем **одна транзакция**: `credited_tx_id`
   + `modifyBalance(... 'deposit' ...)` с идемпотентным ключом. Ключ — `(chain, tx_hash,
   event_index)`: повторный проход слушателя не начислит дважды.
4. `orphaned` (реорг) — деньги не списываются задним числом вручную: создаётся карточка
   Security, потому что это уже инцидент.

Правило: **депозит никогда не начисляется по «увидели транзакцию»**, только по
подтверждённому количеству блоков, и всегда через единственную функцию изменения баланса.

## 5. Поток вывода

Сегодня: заявка `pending` → оператор вводит `tx_hash`. В мультичейне это не масштабируется
(три сети × ручной ввод = ошибки). Проект:

1. Заявка создаётся с `chain` и `address`, деньги списываются одной транзакцией (как сейчас).
2. `broadcast` — подписанная транзакция уходит в сеть; `tx_hash` пишется автоматически.
3. `paid` — по подтверждению; `failed` — с возвратом на баланс (сейчас это `reject`).
4. Идемпотентность: `idempotency_key = withdrawal_id`, повторный broadcast невозможен.
5. Ключи подписи — только у Мастера (см. §7); агент видит адреса и tx_hash, не seed.

## 6. Сверка (reconciliation)

Ежедневно, на каждую сеть: `onchain_balance` (сумма по адресам проекта) против
`ledger_balance` (обязательства по БД). Расхождение > порога — инцидент, а не «подождём».
Существующий `getFinancialReconciliation()` считает только внутренние инварианты; он
остаётся, но дополняется внешней сверкой.

## 7. Границы безопасности

| Что | Кто | Где |
|---|---|---|
| Seed/приватные ключи | только Мастер | хранилище Мастера, не Git, не чат, не логи |
| RPC/API-ключи | Мастер вводит | `.env` прода, не репозиторий |
| Адреса, tx_hash, балансы | агенты | БД, логи без ключей |
| Комиссии и лимиты | настройки + приёмка Security | `settings`, не константы |

Тестнет: TON testnet, BSC testnet, Sepolia. Mainnet включается только Мастером после приёмки
фазы 2 (правило уже записано в регламенте, §7 «Запреты»).

слушателей — только автоматизацию выплат в Ф2.
