# Протокол ходов и доставка

## Виды ходов (kind)
`dispatch` (рабочая карточка), `plan` (очередь Координатора), `review` (приёмка
миссии), `answer` (ответ на вопрос: Warden/Reviewer по умолчанию или точная активная
роль из `need`), `reminder` (напоминание о маркере),
`retry` (компактный повтор), `pilot` (эфемерный прогон VAULT-P1),
`provision` (административный запрос создания/замены Arena-агентов, не миссия и
не рабочая карточка), `arbiter` (D-053 — разбор повторяющейся петли перевыдачи:
не приёмка миссии и не новая карточка), `heal` (D-073 — передача поломки
транспорта закулисному Maintainer'у: не карточка, не миссия, вне очереди). Контракт: `protocolVersion 1.11` (1.1 — provisioning,
1.2 — drive-контракт Gateway 1.8.0/D-033, 1.3 — бюджет overhead и payload-канал
D-034, 1.4 — прайм маркера Координатора и адрес артефактов D-035, 1.5 — хотфикс
длинной зоны роли D-036, 1.6 — мультирепо-сторож ADR D-037, 1.7 — зона роли
как verbatim-факт D-038, 1.8 — total-лимит Executor 7500 D-039, 1.9 — напоминание
маркера без dispatch_id/run_id D-040, 1.10 — обратная связь Координатору блоком
plan.note D-042; аддитивно к 1.0; D-043 — транспорт-внутренний порядок проверки
бюджета выдачи, D-044 — квитанция подтверждённой доставки и восстановление отметки
перед уборкой фантомов; версия контракта не менялась, 1.11 — противоречие
`pr:null`/`merged:true` лечится напоминанием D-046; D-105 аддитивно описывает
необязательный `question` и durable-возврат результата при `gate:true + need`, не
меняя required-поля и `protocolVersion`).

## Арбитраж повторяющейся петли (D-053)
Раньше третья перевыдача одной карточки за шесть часов сразу ставила паузу
`redispatch` и звала Мастера. 07.11 на VAULT-2 · S-4 это повторилось трижды:
исполнитель отдал draft-PR с прямым описанием блокера по Scope, транспорт верно
увидел «нет заявки о мерже» и вернул карточку в Rework — правила сработали, а
разбирать петлю было некому, кроме человека.

Теперь порог перевыдач (`REDISPATCH_LIMIT`) уходит арбитру — роли с функцией
`Reviewer` (в проекте Warden), вид хода `arbiter`, профиль `reviewer.arbiter`,
маркер `CF_ARBITER_RESULT` с `dispatch_id` карточки и `turn_id` разбора.
Дело арбитра собирается заново и только из фактов: поле «Ответ», состояние и
`Check` карточки, состояние PR по GitHub (`merged` / `closed` / `open` / draft),
журнал попыток выдачи, снимок очереди. Отчёт агента в чате доказательством не
считается.

Решения арбитра:

| Вердикт | Что происходит |
|---|---|
| `resolve` + `action:ready` | та же карточка снова в работе; причина и `fix` записаны в «Ответ» |
| `resolve` + `action:rework` | карточка возвращена автору постановки |
| `resolve` + `action:accepted` | работа признана выполненной |
| `resolve` + `action:blocked` | карточка в Blocked, цикл идёт дальше без неё |
| `master` | **цикл остановлен** паузой `arbiter-master` |

После любого `resolve` ход возвращается Координатору с причиной: работу выбирает
он, арбитр лишь снимает петлю. Инварианты: пауза снимается только человеком;
маркер принимается лишь при совпадении карточки и `turn_id` (чужой ответ
сохраняется локально, ожидание не снимается); решение без `reason` не
применяется; арбитр не правит код, карточки и постановку. Пауза `redispatch`
остаётся запасным путём: нет активного Reviewer, дело не читается или исчерпан
`C.arbiterLimit = 2` разбора на карточку — тогда, как и раньше, нужен Мастер
(пауза `arbiter-limit`). Профиль арбитра не несёт блоков записи в git и полного
задания — это проверяет coverage-oracle.

## Маркер без ID выдачи — напоминание, а не пауза (D-040)
Боевой K-21: Executor слил PR, но прислал маркер с `task` вместо
`dispatch_id`/`run_id` и без `status`. Транспорт верно отказал в подтверждении
(защита от зачёта чужой/прошлой попытки), но сразу ушёл в паузу `marker-mismatch`,
минуя напоминания, — цикл встал при сделанной работе. Теперь ветка mismatch
различает два случая (`dispatchIdState`):
- **ID выдачи нет** (`missing`: ни один присутствующий ID не противоречит выдаче,
  но `dispatch_id`/`run_id` не хватает) — формат-дефект. Шлётся до
  `markerReminders` напоминаний `reminder.marker` с `why=ids`: точные ID уже в
  промпте, агента просят повторить **только маркер**, работу не переделывать.
- **ID чужие/битые/противоречащие** (`conflict`) — возможен ответ прошлой выдачи:
  прежняя сразу-пауза `marker-mismatch`, копия ответа сохраняется локально.
Проверка ID **не ослаблена**: значения не подменяются (`adoptIds`), запись в
Notion по неверному ID не идёт; после исчерпания напоминаний — пауза. Бюджеты не
подняты (`reminder.marker` ≤700, total ≤900). Регрессия —
`relay-marker-ids-reminder-integration` и `relay-review-dispatch-integration`.

## Запасной fetch с таймаутом — выдача не зависает посреди Running (D-041)
Боевой VAULT-1: после маркера Координатора выдача поставила карточку в Running,
затем `gateway("append")` завис на запасном `fetch` **без таймаута**. Лог «Выдан
ход» и `sendToRole` (ожидание + промпт) не выполнились; сторож тишины через 131 с
перезапустил шаг, и Координатор получил план заново при живой карточке. Причина:
GM-путь ограничен (`requestOnce` 45 с), а запасной `fetch` в шлюзе и ntfy шёл без
`AbortController` и мог висеть вечно; сетевой запрос не отмечает жизнь (`busyAt`),
поэтому сторож (120 с) срабатывал посреди выдачи. Теперь каждый запасной `fetch`
идёт через `fetchWithTimeout` с таймаутом по своему GM-пути: **шлюз 45 с, ntfy
15 с**. Отказ становится явным и ловимым: `gateway("append")` в `dispatchTask`
обёрнут в `try/catch` — незаписанный журнал попытки логируется, выдача продолжается
(карточка Running, промпт уходит агенту), а не зависает. Отметку жизни `fetch` не
ставит. **Агентский контракт не менялся — protocolVersion остаётся 1.9**; фикс
транспорт-внутренний. Регрессия — `relay-fetch-timeout-integration`.

## Обратная связь Координатору доходит до промпта (D-042)
Боевой VAULT-1 · K-22 «Ратификация решения GameSpec и локализационного контракта»:
Contract Architect выполнил работу (PR vault#9 слит → Submitted), но Координатор
вернул карточку в Ready с «Кому» = Warden и трижды назвал `next:"Warden"`. Транспорт
трижды верно отказал (`decisionRoute` → ask) и встал в паузу. **Warden (Reviewer) —
главный по организации процесса: рабочих карточек не принимает, к нему обращаются
только через обратную связь** (вопросы/ответы и приёмка миссии через `next:"done"`).
Иначе Координатор начинает выдавать ему задания, и приёмщик превращается в Auditor.

Причина петли оказалась не в «упрямстве», а в потере обратной связи: заметка отказа
(`note`) передавалась в `requestPlan` → `coordinatorPrompt`, но **не попадала в
compile-контекст**, и блока `plan.note` не существовало. Координатор получал тот же
снимок очереди («K-22 (Warden, Sequence …)») без объяснения и повторял запрещённый
ход. Guard работал, объяснить причину не мог. Та же потеря касалась всех заметок:
dispatch-miss, Submitted/Rework, reviewer-отказ.

Теперь заметку рендерит verbatim-блок **`plan.note`** («Обратная связь транспорта: …»)
в профилях `coordinator.plan` и `coordinator.recovery`; `coordinatorPrompt` кладёт
`note` в контекст, `requestPlan` передаёт его и в recovery-envelope. Отказ Reviewer
стал исполнимым: названо поле **«Кому»**, перечислены активные Executor/Auditor,
сказано оставить карточку в Ready и повторить `next`; ратификация решений, статус
ADR и правка файлов названы работой исполнителя. Защита не ослаблена: Reviewer
по-прежнему не получает карточку (`ask`, не dispatch), пауза после трёх попыток
сохранена; `note` не подменяет решение и не конвертирует карточку в вопрос/done.
Бюджет overhead `coordinator.plan` — **3400** с D-092: подъём на 200 знаков
оплачивает права Координатора на процессные поля «Ролей» (Зона записи, Гейт,
Репозиторий, Функция) по решению приёмки. Это инструкция, а не данные, поэтому
она не сжимается (D-078); подъём записан в `contracts/agent-protocol.json` → `d092`.
До D-092 бюджет был 3200 и не поднимался — `plan.note` verbatim.
**protocolVersion 1.10** (аддитивно). Регрессия —
`relay-coordinator-note-delivery-integration`.

## Бюджет выдачи проверяется до Running (D-043)
Боевой VAULT-1 · K-29 «Вендоринг CJK-шрифтов…»: карточка без отдельного payload дала
**total 10381 > 7500** (оракул 4232 знака, Scope 1435, инварианты 1035, намерение 626).
Payload-канал D-034 выносит только прикреплённое тело задания, а оракул/Scope/инварианты
остаются inline verbatim; compact для dispatch выбирает тот же полный профиль. Поэтому
большая карточка честно не прошла жёсткий лимит — это не сбой Warden и не сеть.

Дефект был в порядке и диагностике: `dispatchTask` создавал журнал и ставил Running ДО
сборки промпта, затем откатывал Ready, а null от отправки ошибочно назывался «то же
сообщение уже уходило». Теперь промпт собирается **до журнала и patch Running**; отказ сборки
возвращается Координатору строкой и доходит блоком `plan.note` (D-042). Карточка остаётся
Ready, агенту ничего не уходит, журнал выдачи не создаётся. Счётчик
`cfn-dispatch-miss` сбрасывается только после успешной сборки, поэтому третий подряд отказ
по-прежнему ставит паузу. Подсказка исполнима: убрать повторы/справочные детали, при
необходимости разбить работу на последовательные карточки с полными условиями и Dependency,
не ослаблять и не обрезать оракул; `Payload Drive File ID` вмещает большой текст задания,
но не заменяет inline-оракул/Scope. Total-диагностика показывает размеры fact-блоков
(`task.acceptance`, `task.scope`, …), а не нулевой overhead marker/git; overhead-диагностика
D-034 сохранена. Поздний fail-closed guard компилятора остаётся запасным путём.

**Бюджеты не подняты, требования не обрезаны.** Агентский контракт не менялся —
protocolVersion остаётся **1.10** (транспорт-внутренний фикс, секция `d043`). Регрессия —
`relay-dispatch-budget-preflight-integration` на дословной фикстуре K-29.

## Подтверждённая доставка не теряется уборкой фантомов (D-044)
Боевой VAULT-1 · K-30: журнал зафиксировал «Задание отправлено» с id сообщения, агент
закончил ход и прислал маркер этой dispatch/run-пары, но позднее `expect.sentAt` оказался
пуст — и уборка фантомов ложно вернула карточку в Ready («отметки отправки нет»). Работа и
ответ были; откат — ошибка транспорта.

Подтверждение доставки теперь живёт не только внутри `expect`. `consumePending` после
подтверждённой доставки пишет отдельную квитанцию `cfn-delivery-receipts-v1`
(kind/ref/runId/turnId/questionId/roleId, messageId, sentAt, watermark, seen) **до** снятия
очереди. Если сообщение в чате есть, а ожидание потеряно или подменено, ставится пауза
`delivery-state-lost`, а не молчаливый успех. Перед откатом `dropGhostHandoff` восстанавливает
`sentAt/verified/watermark` по квитанции или по своей реплике с точными dispatch/run ID в чате
адресата; карточка не трогается, ответ читается дальше. Второй ghost-проход тика решает по
живому GM-состоянию, а не по устаревшему снимку.

Настоящий фантом без квитанции и без реплики этой выдачи по-прежнему возвращается в Ready.
Чужой/прошлый run не принимается, чужая страница не читается как чат адресата, ID не
подменяются. Намеренный отказ доставки (капча, ошибка Arena, повтор) гасит квитанцию;
мёртвая реплика (`deadSend`) и очередь с капчей не принимаются за доказательство. Агентский контракт не менялся — protocolVersion остаётся **1.10**
(транспорт-внутренний фикс, секция `d044`). Проба — `relay-delivery-receipt-smoke`.

## Маркер противоречит себе: `pr:null` + `merged:true` (D-046)
Явный `pr:null` означает «PR не будет», `merged:true` — «PR слит». Вместе они
означают «PR нет, но он слит» — такую заявку нельзя ни принять, ни молча
пропустить: пропуск позволил бы провести код в main без сверки репозитория и
базовой ветки. Поэтому маркер разбирается отдельно от «PR не нужен»:

- **Напоминание, а не Blocked.** Такой маркер уходит в общую лестницу
  `markerMissing(..., "pr-claim")` — до `C.markerReminders` (2) напоминаний.
  Карточка и журнал не меняются, ожидание остаётся живым; после исчерпания —
  обычная пауза `kind:"marker"`. Агент правит **только строку маркера**: работу
  и отчёт не повторяет.
- **Что считается противоречием.** Поле `pr` присутствует, его значение —
  `null`/`none`/`нет`/`-`, и при этом заявлен мерж (`merged:true` или
  `status:"merged"`). Пропущенное поле `pr` остаётся забывчивостью (Rework), явный
  `pr:null` с `merged:false` — законный исход без PR. Аудитор и Reviewer в эту
  ветку не попадают: у них PR нет по роли.
- **Почему это вообще случалось.** Промпт сам предлагал такую пару: в шаблоне
  маркера рядом с `"pr":"<URL|null>"` стоял литерал `"merged":true`, а правило
  читалось как «merged:true после мержа». Теперь шаблон печатает `"merged":false`,
  а правило связывает поля: «без PR pr:null,merged:false; merged:true только после
  мержа». `projectPrBoundary`, `ensureMerged`
  и проверка repo/base не менялись, бюджеты не поднимались.
- **Пробы.** `relay-pr-claim-conflict-smoke` (дословный боевой маркер K-34 в обоих
  профилях) и усиленный `relay-no-pr-smoke`: прежний срез вырезал `prDeclined` без
  `ACTIVE_PROFILE`/`hasMergedClaim`, поэтому неlegacy-путь не проверялся и баг
  прошёл в 1.12.10.

## Компиляция
`compilePrompt(request)` выбирает профиль, проверяет обязательные факты
(`missing_fact`), запрещённые блоки/аудитории (`forbidden_block`), маркер
(`marker_mismatch`), бюджет (`budget_exceeded`) и неизвестный профиль
(`unknown_profile`). Ошибка компиляции → локальная пауза, отправки нет.
D-034: `budget_exceeded` несёт разбивку по блокам (`id/chars/overhead/verbatim`),
и пауза называет топ блоков, съевших overhead, — причина диагностируема, а не
«overhead N > лимита».

## Payload-канал (D-034)
Папка `Arena/<project>/payloads` больше не простаивает. Большое задание
(длиннее `payloadInlineMax`, по умолчанию 1500 символов) не инлайнится в промпт:
на каждый прогон транспорт фиксирует снимок через Gateway `savePayload`
(`<dispatch_id>_<run_id>__assignment.md`, как журнал в `logs`) и доставляет
короткий **verbatim-указатель** на него. Снимок стабилен, даже если исходный
payload отредактируют во время хода. Стратегия доставки:
`full → payload-указатель → compact → pause`.

- **Оракул и Scope остаются inline** в промпте; payload-файл их не заменяет и не
  ослабляет. Указатель лишь отсылает к развёрнутому заданию.
- Малое задание остаётся инлайном (`full`), файл не создаётся.
- Отказ `savePayload`/`read` — явная ошибка/пауза, а не тихий инлайн.
- Указатель — verbatim-блок `task.assignment`, поэтому overhead он не увеличивает.

## Маркер Координатора и адрес артефактов (D-035)
Два дефекта боевого хода VAULT-1 и их исправление (бюджеты **не подняты**):

- **Прайм маркера.** Маркер стоит только в конце длинного `coordinator.plan`, и
  после десятка tool-вызовов Координатор его «не видел» и честно отказывался
  выдать («формат не виден, по памяти не восстанавливаю»). Теперь
  `coordinator.plan`/`coordinator.recovery` открывает короткий блок
  `coordinator.prime`: «заверши ход маркером последней строки, формат и IDs — в
  конце промпта». Авторитетный маркер с IDs остаётся последним блоком. Блок
  прайма не несёт литерал маркера и не называется `marker.*` — инвариант «ровно
  один маркер, и он последний» не нарушается.
- **Адрес артефактов.** Раньше раскладку Drive (`drive.layout`) получал только
  Координатор, поэтому исполнитель/аудитор не знали папку `artifacts` и клали
  отчёты в корень Диска. Теперь `executor.card`/`auditor.card`/`reviewer.card`
  несут короткий блок `drive.artifacts`: «Артефакты в `Arena/<project>/artifacts`,
  не корень Диска; ссылки в поле `artifacts`». Имя проекта берётся из профиля
  (`driveFolder`), не зашито. Блок влезает в бюджет `auditor.card` ≤2200 без его
  подъёма (K-17-подобная карточка проходит). Отчёты, уже лежавшие в корне,
  перенесены в `artifacts` (перенос не меняет ID/URL; ретро-переименование
  запрещено D-031).

**Хотфикс D-036 (1.12.1).** Блоки D-035 съели запас бюджета, а боевая зона роли
оказалась длинной (~150 зн. против ~35 в фикстуре K-17): карточка K-20 дала
overhead 2209 > 2200 (`auditor.card`), план Координатора — 3202 > 3200. Лечение
без подъёма бюджетов: `coordinator.prime` и `drive.artifacts` урезаны;
`marker.agent` аудитора больше не объясняет `pr/merged` — этих полей нет в его
маркере. Регрессия закрыта пробой K-20 с длинной зоной (`prompts-smoke` §14–15).

**Мультирепо-сторож ADR D-037 (1.12.2).** Сторож `refreshDecisions` обходит все
репозитории профиля (`C.repos`), а не только главный `C.repo`. Раньше предложение
из второго репозитория (например `vault`) не находилось: главный репозиторий
профиля (`vault`) не содержит `docs/decisions`, запрос давал 404, сторож
молча возвращал пустой снимок, и полный текст с Git blob SHA не дописывался в
вопрос — предохранитель не пропускал его к приёмке. Теперь 404 папки одного
репозитория не останавливает обход; кэш `cfn-adr-text` составной (`repo/file`) с
миграцией плоских ключей; строка предложения несёт свои `repo`/`branch`, из них
строятся ссылка и ключ дедупликации. Дедупликация по имени файла кросс-репо
сохранена: имена ADR должны быть уникальны в профиле. Регрессия —
`relay-adr-multirepo-integration`. Бюджеты промптов не менялись.

**Зона роли как verbatim-факт D-038 (1.12.3).** Боевая карточка K-21 (Executor
Core, зона ~158 зн.) пробила бюджет `executor.card` (overhead 2859 > 2800): зона
роли инлайнилась в `authority.core` и считалась overhead. D-036 закрыл
`auditor.card` и `coordinator.plan`, но `executor.card` с длинной зоной не
проверялся. Лечение без подъёма бюджетов: зона роли — это факт (как `task.scope`),
вынесена в verbatim-блок `role.zone` и не входит в overhead; `authority.core`
несёт только правило о зонах. `role.zone` добавлен во все профили с
`authority.core` (executor/auditor/coordinator/reviewer) и запрещён в
continuation/pilot. Команда мержа больше не дублируется в `authority.executor`
(остаётся в `git.executor`). Overhead `executor.card` теперь не зависит от длины
зоны (~2678, запас ~122). Регрессия — `prompts-smoke` §16 (K-21). Бюджеты промптов
не менялись.

## Доставка и повтор
Классы отказов: `editor_not_found`/`send_disabled`, `captcha`, `auth`/
`agent_unavailable`, `tool_call_limit`, `rate_limit`, `arena_generic_error`,
`network`, `budget_exceeded`, `unknown`. Только `arena_generic_error` даёт один
компактный повтор того же хода (plan → coordinator.recovery, dispatch →
delivery.compact). Капча/auth/rate_limit — пауза до человека. Журнал попытки хранит
профиль, блоки и их версии/хеши, метрики, попытку и исход (кольцо 200).

Compact-retry ролевой: `delivery.compact` для Auditor содержит read-only границу
(без коммитов, push и PR merge); Reviewer рабочую выдачу через compact не получает
(guard); Executor мержит сам. Coverage-карта проверяет git-границы compact/recovery
и continuation по роли, а не только по маркеру.

## Tool-call limit: продолжение хода
Состояние Arena «The agent reached the tool-call limit for this turn. Send a
message to continue where it left off.» — отдельный класс `tool_call_limit`
(определяется раньше `budget_exceeded`/`rate_limit`/`arena_generic_error`). Ход уже
начался, часть работы могла быть сделана. Действие — короткое сообщение-продолжение
в тот же чат (`continuation.*`), а не повтор задания, не compact-retry и не
напоминание о маркере.

- Детект: `role=status`/`alert` в транскрипте (amber — доп. признак), не в
  pre/code/diff/textarea/редакторе; привязка к ближнему `chat-message`; дедуп по
  `tool-limit:<messageId>` (без id — хеш текста+позиция).
- Продолжение сохраняет исходные IDs (dispatch/run, mission/turn, question/turn) и
  маркер вида хода; маркер — только после фактического завершения. Overhead ≤700
  (pilot ≤250). Запрещены блоки полного задания, очереди, регламента и pilot-блоки
  в командных профилях. Ошибка компиляции continuation → пауза, не отправка.
- Лимит `toolLimitContinueMax = 2`: исходный ход → 1-е продолжение → 2-е → пауза и
  Мастер. Пауза раньше лимита: нет прогресса после продолжения, провал отправки,
  несовпадение страницы/роли, ход уже завершён маркером.
- Состояние: `toolLimitContinuations`, `lastToolLimitMessageId`, `lastToolLimitAt`,
  `toolLimitNoProgress`, `continuationWatermark`. Не смешивается с `arenaResend`,
  `tries`, `branchResend`. Карточка Notion, PR, Check, Submitted At, Output Drive
  File ID и Run/turn/question IDs не меняются; новый Run ID не создаётся.
- Журнал: `tool_limit_continued`/`tool_limit_paused`/`tool_limit_no_progress`,
  `errorClass: tool_call_limit`, `profileId: continuation.*`, attempt, messageId,
  chars/utf8Bytes. Исходный watermark не сдвигается: финальный отчёт собирает части
  до лимита и после; continuation-сообщение ScriptCat не становится частью отчёта.
- Pilot VAULT-P1: `continuation.pilot` без CF_* и внутренних ссылок, свой namespace.

## Provisioning Arena-агентов (1.10.0)
`admin.provision` — отдельный административный профиль. Аудитория: активная роль
с `Agent Admin=true` (предпочтительно Coordinator, иначе Reviewer). Обязательные
факты: `provision.requestId`, `provision.candidates`. Блоки: `identity.provision`,
`authority.provision`, `provision.candidates`, `provision.policy`,
`marker.provision`. Запрещены mission/queue/git/pilot-блоки и обычные маркеры
ходов. Overhead ≤1800. Ответ завершается одним `CF_AGENT_PROVISION_RESULT` с
тем же `request_id`; `jobs` содержит только `role_page_id` из отправленных
кандидатов, `action` только `create|replace`. Пустой `jobs` допустим. Команды
`archive/delete/activate/admin` как отдельные команды запрещены; архивация
старого агента — внутреннее следствие `replace`, а не команда маркера.

Provisioning не пишет `K.pending/K.expect`, не создаёт страницы Notion и не
запускает рабочий цикл. Во время запроса/job автоцикл выключен; после успеха
восстанавливается, если не было паузы. Право одобрения проверяется по свежей
строке Notion, а не по имени роли.

## Вопрос с gate/need — это ход к адресату (D-091)
Боевой VAULT-3: Координатор выдал Rework B0-r2, записал разбор и попросил решение
приёмки «здесь и сейчас» — `question` с вариантом по умолчанию, `need:"Warden"`,
`gate:true`, и `next:"Warden"`. Первые шаги прошли правильно: вопрос лёг строкой и
попал в очередь приёмки. А дальше ход ушёл в `decisionRoute("Warden")`, отказал
(приёмке карточек не выдают), вернулся Координатору с советом «смени «Кому» на
рабочую роль». Очередь была пуста, выдавать было нечего, и он закончил ответ без
маркера.

Причина в транспорте: гейт-вопрос и `next` считались независимыми. `startAnswer`
в этой ветке звался, но не был условием ветки: при повторном вопросе `askQuestion`
отдаёт `{ id: "" }` (строку не пишем второй раз), ячейка в очереди по пустому id
не находилась, `if` тихо не срабатывал — и ход продолжался по `next`, которого
для вопроса не существует.

Теперь вопрос, который держит ход, сам передаёт ход адресату: `startAnswer` →
`return true`, `next` в этом ходе не читается — журнал говорит это прямо.
Неудача передачи (нет ячейки, транспорт не поставил очередь) — пауза
`answer-handoff` класса `transport`, а не молчаливый возврат Координатору.
Ячейка ищется и по тексту вопроса: `id` пуст при повторе — это и был отказ 09.11.
`next:"blocked"` разбирается своей прежней веткой, без дублирования.

Роль не изменилась: приёмка по-прежнему не получает рабочую карточку. Но отказ
`decisionRoute` на приёмку теперь отделяет два разных дела — «спросить можно и
нужно (question с gate+need), рабочую роль для вопроса называть не нужно» и
«карточку приёмке не выдают — смени «Кому» на Executor/Auditor». Раньше эти
фразы были одной, и Координатор читал запрет выдачи как запрет вопроса.
**protocolVersion остаётся 1.11** (аддитивно, форма маркера не менялась).
Регрессия — `relay-answer-handoff-smoke`, обновлены `relay-answer-smoke` и
`relay-question-gate-smoke`.

## Durable-возврат результата по `gate` (D-105)

В каждом result-маркере `question` — необязательное поле; объект вопроса несёт
`text`, полный `default` и при необходимости `options`, `gate`, `need`. Обычный
вопрос не меняет текущий маршрут. `need` без `gate:true` игнорируется, а `gate:true`
без точного активного `need` не удерживает ход. Только пара
`question.gate=true` + `question.need="<точное имя активной роли>"` включает
адресный gate.

Для такого gate транспорт сначала сохраняет в durable-очереди полный исходный
результат: marker, `kind`, `ref`, исходный `run_id`/`turn_id`, снимок ожидания и
объект решения. До ответа этот результат не применяется. Ответный ход `answer`
адресуется точной активной роли из `need`; неизвестный, отключённый или
неоднозначный адресат не заменяется Reviewer/Coordinator по умолчанию.

После ответа в «Обратной связи» возврат сохраняется отдельной квитанцией ДО
очистки живого ожидания. Транспорт отправляет его исходному автору по точному
`sourceRoleId`; только подтверждённая доставка восстанавливает отложенный ход.
Перед применением заново сверяются `question_id`, UUID возврата, исходная роль,
маркер и исходные `kind/ref/run_id/turn_id`. Результат продолжается с теми же
исходными ID; повтор после перезагрузки идемпотентен, несовпавшее ожидание не
перезаписывается. Если Мастер уже поставил «Решено» в Notion, сохранённый ответ
не переписывается. Адресная реплика и весь хвост после неё исключены из исходного
отчёта/журнала.

Особый маршрут Coordinator сохраняется: ответ на его плановый вопрос
возвращается ему новым планом, а строку «Обратная связь» создаёт транспорт,
не Координатор вручную. Пробы — `relay-deferred-result-smoke.mjs`,
`relay-log-answer-smoke.mjs`, `relay-answer-smoke.mjs` и `prompts-smoke.mjs`.
`protocolVersion` остаётся **1.11**: поля вопроса необязательны, required-поля
существующих маркеров и их ID не меняются.

## Инварианты
- #37: `Check=fail` не выдаётся как Rework+Ready одним ответом.
- #38: recovery Координатора — не новый dispatch.
- #40: `verdict:master` сохраняет question_id/turn_id; поздний маркер принимается
