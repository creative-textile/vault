# Правила PR: как агенты делят один репозиторий

Документ для всех ролей, которые коммитят в `vault` и в свои
репозитории (`vault`, `pilot`, `campaign-1`). Написан по фактам, а не по
намерениям: раздел «Почему так» объясняет каждое правило боевым случаем.

## Что произошло и почему это не «сломанный git»

Истории в репозитории **связаны**. Проверено: `git rev-list --max-parents=0`
даёт один корень, `git merge-base main <ветка>` находится, `git rev-list --count
origin/main` — 107 коммитов. Если при merge приходит «refusing to merge unrelated
histories», значит клон **усечён** (`--depth=1` или свежий клон с одним
коммитом). Лечится одной командой:

```bash
git fetch --unshallow origin        # либо, если клон не помечен shallow:
git fetch --deepen=100 origin main
```

Проверить себя: `git rev-parse --is-shallow-repository` → `true` значит клон
усечён. В таком клоне `git rev-list HEAD..origin/main` показывает **ноль** даже
когда main ушёл вперёд — так и родилось «новых коммитов нет, мержить нечего».

Агенты получают рабочую копию от платформы и не выбирают глубину клона. Поэтому:
**если merge требует `--allow-unrelated-histories` — это признак усечённого
клона, а не двух историй.** Не разрешайте конфликты в таком состоянии: сначала
`--deepen`, потом обычный merge. Иначе вы сравниваете свою правку с пустотой и
получаете add/add по всем файлам.

## Почему конфликты всё равно будут (и где именно)

Один выпуск транспорта обязательно трогает **одни и те же семь файлов**.
Замер по последним 40 коммитам:

| файл | коммитов | почему |
|---|---|---|
| `docs/DECISIONS.md` | 38 | каждый выпуск дописывает запись в конец |
| `tools/script-cat/relay.user.js` | 32 | **генерируется** сборкой из `src/` |
| `tools/script-cat/contracts/agent-protocol.json` | 32 | каждый выпуск дописывает ключ `dNNN` |
| `tools/script-cat/src/00-header.js` | 30 | номер версии |
| `tools/script-cat/src/04-notifications.js` | 30 | номер версии |
| `tools/script-cat/tests/docs-smoke.mjs` | 26 | каждый выпуск дописывает блок проверки |
| `tools/script-cat/tests/dispatch-coordinator-smoke.mjs` | 25 | счётчик сюит |

Два агента, выпустивших по правке параллельно, конфликтуют **гарантированно** —
не потому что плохо работали, а потому что оба дописали в конец одного файла.
Это структурная проблема, а не дисциплинарная.

## Правила

### Р1. Один PR — одна карточка, один номер решения

Смешанный PR (правка транспорта + документ + чужая правка «заодно») нельзя ни
проверить, ни откатить. Номер решения занимается **в момент создания PR** и
сверяется с `main` перед push:

```bash
git show origin/main:docs/DECISIONS.md | grep -c '^## D-'
```

Если ваш номер уже занят — берите следующий. Гонка номеров реальна: 10.11 два
агента одновременно взяли D-095, и один пришлось перенумеровать после влития.

### Р2. Перед push — merge `main` в свою ветку, а не наоборот

```bash
git fetch origin main
git merge origin/main        # конфликты разрешаются у себя, а не в PR
npm run verify               # 139+ сюит, сборка, guard, регрессия
git push
```

Вливать `main` в конце (когда PR уже открыт) — значит отдать конфликт туда, где
его будет разрешать следующий агент или человек, вслепую.

### Р3. `relay.user.js` не мержится руками. Никогда

Бандл — 20 515 строк и 1,3 МБ, он **генерируется** из `tools/script-cat/src/**`.

- Вливать его вручную бессмысленно: git вставит маркеры внутрь кода и
  предложит выбрать сторону целиком.
- Порядок при конфликте: взять любую сторону, затем `npm run scriptcat:build`,
  затем `npm run scriptcat:check`.
- Правильный результат — тот, что собрался из разрешённых исходников. Ручной
  merge 20 тысяч строк гарантирует тихую потерю чужой правки.

### Р4. `docs/DECISIONS.md` — union-merge

Файл только дописывается в конец, поэтому при конфликте разрешайте его **union**
— сохраняйте обе стороны, а не одну:

```bash
git merge-file --union <(git show :2:docs/DECISIONS.md) \
  <(git show :1:docs/DECISIONS.md) <(git show :3:docs/DECISIONS.md) \
  > docs/DECISIONS.md      # затем eyeball-проверка:
grep -n '^## D-' docs/DECISIONS.md | tail -5
```

Номера должны идти по возрастанию, а текст **обеих** записей — остаться.
Автоматически это сделает `merge=union` в `.gitattributes`, но сейчас там нет
ни строки, и добавлять его без решения не стоит: `union` опасен для остальных
файлов, а `.gitattributes` действует на весь репозиторий.

### Р5. Версию поднимает только тот, кто выпускает транспорт

Номер версии живёт в двух файлах и меняется одним коммитом с решением. Если ваш
PR **не меняет** `tools/script-cat/src/**`, версию не трогайте: правка docs,
тестов или правил сборки выпуском не является. Это снимает половину ложных
конфликтов в `00-header.js` и `04-notifications.js`.

### Р6. Один PR на транспорт — одновременно

Все правки транспорта идут через Maintainer'а, и он берёт **замок**: метка
`transport-lock` на PR. Пока метка на чужом открытом PR, свою правку транспорта
не начинайте — очередь, а не параллель. Причина арифметическая: Р2 требует
merge `main`, и если два транспорта идут одновременно, второй мержит первый, у
которого ещё не влит результат — снова конфликт в тех же семи файлах.

Замок снимается влитием или закрытием PR. Забытая метка — не повод ждать сутками:
если PR без движения 24 часа, замок снимает Coordinator по решению приёмки.

### Р7. Зона роли — граница PR, а не пожелание

Смотрите «Репозиторий» и «Зону записи» в базе «Роли». PR, трогающий файлы вне
зоны, отклоняется — даже если правка правильная. Локальная проверка:

```bash
git diff --name-only origin/main...HEAD
```

Машинно это проверяет `npm run preflight -- --zone "tools/script-cat/**"`
(см. ниже) и печатает файлы вне зоны.

### Р8. PR живёт часами, а не сутками

Долгоживущая ветка = накопленный конфликт. Открывайте PR сразу (можно черновиком
`gh pr create --draft`), вливайте в тот же рабочий цикл. Если правка не влезает
в цикл — режьте на карточки, а не тяните ветку.

### Р9. Вливать `--merge`, не `--squash`

История выпусков нужна для отката (`D-09x` в сообщении коммита) и для разбора
«на какой сборке сломалось». Squash склеивает выпуск и правку в один коммит, и
`git log --oneline` перестаёт отвечать на вопрос «что вошло в 1.14.24».

### Р10. Сомнение — Карточка, а не правка

Если правка требует чужой зоны или чужого решения — вопрос в «Обратную связь»,
а не коммит «на всякий случай». Разбор идёт по карточке; влитая «на всякий
случай» правка всплывёт через неделю без автора.

## Механика: `npm run preflight`

Проверка перед push, одна для всех ролей:

```bash
node tools/script-cat/preflight.mjs                       # общие проверки
node tools/script-cat/preflight.mjs --zone "tools/script-cat/**"
```

(Скрипт `npm run preflight` появится, когда его добавит Maintainer отдельным
решением — правка `package.json` вне зоны исполнителя.)

Что проверяет:

1. клон не усечён — иначе `git rev-list HEAD..origin/main` врёт «0 новых
   коммитов» (проверено на живом клоне: shallow, при этом main ушёл вперёд);
2. ветка не отстала от `origin/main` (иначе — `git merge origin/main`);
3. `relay.user.js` соответствует исходникам (`build.mjs --check`);
4. ровно одно новое решение `D-NNN` и его ключ есть в контракте;
5. версия поднята **только** если менялся `src/**`;
6. файлы вне зоны роли (если передана `--zone`);
7. нет маркеров конфликта в начале строки (`<<<<<<<`) ни в одном файле.

Код возврата 1 — push не делать. Вывод — по-русски, с готовой командой для
исправления.

## Что стоит сделать дальше (решает Мастер)

Три структурные правки снимают конфликты навсегда. Каждая — отдельное решение,
потому что касается всех ролей сразу:

1. **`DECISIONS.md` разложить по файлам** (`docs/decisions/D-097.md`) и собирать
   индекс скриптом. Тогда два агента физически не могут править один файл.
   Цена: правка `docs-smoke`, перенос 96 записей скриптом.
2. **Контракт разложить так же** (`contracts/decisions/dNNN.json`) — сейчас
   каждый выпуск дописывает ключ в общий JSON, и это валидный JSON только пока
   его правит один человек.
3. **Убрать `relay.user.js` из git**: он генерируется и весит 1,3 МБ; место
   сборки — артефакт выпуска (Drive/GitHub Release), а не репозиторий. Цена:
   меняется установка (Мастер качает артефакт, а не файл из репозитория), и
   `build --check` перестаёт быть гейтом — его заменяет сверка артефакта.

Пока эти три не сделаны, Р1–Р10 — рабочая дисциплина, а не гарантия. Гарантию
дают только разные файлы на разные правки.
