# Среда разработки и тестовый контур (без Docker)

Версия 1.0 · 2026-11-12 · фаза 0 · владелец: Platform Architect.

## 1. Требование Мастера

> «Тесты должны быть полностью возможны на Supabase + Vercel, без Docker.»

Отсюда три следствия, которые определяют всю подготовку:

1. **Агент обязан проверить изменение без Docker.** Если проверка требует локального контейнера,
   она не считается проверкой: песочница агента не тянет Docker, а вы работаете на телефоне
   или на машине без него.
2. **Тестовая база — облачная и одноразовая.** Supabase даёт PostgreSQL, к которому можно
   подключиться `psql` и который можно пересоздать.
3. **Продакшен переезжает на платный сервер позже** отдельным решением — и тогда Docker может
   вернуться, но как способ запуска, а не как условие разработки.

## 2. Что уже есть в репозитории

| Что | Где | Docker нужен? |
|---|---|---|
| Backend: типы и 7 режимов смоук-тестов на `pg-mem` | `backend/tests/smoke.cjs` | **нет** |
| Схема: `init.sql` + `schema-check.sql` | CI на `postgres:16`, локально — `psql` в Supabase | нет (psql) |
| Frontend: типы, математика 3D, сборка | `frontend/` | нет |
| Bot: типы и сборка | `bot/` | нет |
| Транспорт и документы | `npm run verify` | нет |
| Образы и `docker compose config` | CI `docker` job | только в CI |

Ключевое: **смоук-тесты денег и игр не требуют живой базы** — они работают на `pg-mem`
(PostgreSQL в памяти). Это значит, что агент может доказывать логику без сети, без Supabase и без
Docker. Облачная база нужна там, где проверяется сама схема и миграции.

## 3. Контур Supabase

Проект Supabase создан: `yyvukjxombstglgmnvmp` (пока пустой). Правила работы с ним:

1. **Схема применяется двумя файлами** и только так:
   ```sh
   psql "$SUPABASE_DB_URL" -v ON_ERROR_STOP=1 -f backend/src/db/init.sql
   psql "$SUPABASE_DB_URL" -v ON_ERROR_STOP=1 -f backend/src/db/schema-check.sql
   ```
   Второй прогон `init.sql` обязателен: схема должна быть идемпотентной (это делает и CI).
2. **Данные теста — не в боевой базе.** Для прогонов с реальными суммами создаётся отдельная
   схема (`test_*`) или проект-ветка Supabase; одноразовость важнее удобства.
3. **Секреты — только в Vercel/Supabase/GitHub Secrets.** Строка подключения не попадает в
   репозиторий, в чат и в логи. Если попала — ротация пароля.
4. **Прямой доступ к продакшен-базе из песочницы агента запрещён.** Агент работает с тестовой
   базой; боевая — только через деплой и только с одобрения Мастера.

## 4. Контур Vercel

Проектов пока нет (0). План:

| Часть | Куда | Почему |
|---|---|---|
| Frontend (Vite SPA) | Vercel, статика | бесплатный тариф, preview-деплой на каждый PR |
| API + WebSocket | **не Vercel** (Express + socket.io не живут в serverless) | нужен постоянный процесс; на тестовом этапе — платный мини-инстанс или бесплатный хостинг с ограничением по времени сна. **Docker здесь уместен**: тот же образ, что у вас локально, разворачивается на VPS в один шаг |
| Бот | там же, где API | один процесс на тест, не три |

Это честное ограничение, о котором лучше сказать сразу: **Vercel закрывает фронтенд, а не
бэкенд**.

### Docker и Vercel — не или/или, а разные роли

Мастер спросил прямо: «можно же сделать, чтобы открывалось и с Vercel в облаке, и с Docker на
компьютере — в чём разница?». Разница не в том, что работает, а в том, **кто получает доступ и
что проверяется**.

| | Docker на вашем компьютере | Vercel в облаке |
|---|---|---|
| Кто может открыть | **только вы** — адрес `localhost` живёт на одной машине | **любой**, кому дали ссылку, включая вас с телефона |
| Что видит агент Arena | **ничего** — мой runtime отдельный, ваш Docker мне недоступен | страницу по HTTPS и логи деплоя |
| Что проверяется | «запускается ли у меня» | «работает ли на чужом железе, с HTTPS и мобильным браузером» |
| Кто выполняет проверку | **вы**, вручную | CI/агент, автоматически |
| Стоимость | $0 | бесплатный тариф хватает для превью |
| Секреты | в `docker-compose` / `.env` на вашей машине | переменные окружения платформы |

Четыре следствия, которые важны именно для нас:

1. **Доказательство.** «У меня запустилось» — это ваш отчёт, который я не могу проверить.
   «Открывается по ссылке Vercel» — проверяемо: я могу загрузить страницу и увидеть то же, что вы.
   Поэтому **источник правды — облачный контур**, а Docker остаётся удобным личным инструментом.
2. **Мобильный приоритет.** Вы тестируете с телефона; `localhost` на телефоне — это не ваш
   компьютер. Vercel-preview даёт настоящую HTTPS-ссылку, по которой с телефона открывается
   именно то, что соберётся у игрока.
3. **Параллельность.** Пока Docker занят на вашей машине (или она выключена), агент продолжает:
   его цикл «изменил → `npm test` → задеплоил превью» от вашего компьютера не зависит.
4. **Цена расхождения.** Если проект собирается только в Docker, агент этого не увидит и не
   починит сам — каждая такая проверка становится вашей ручной работой. Это ровно та ошибка,
   из-за которой «тормозило на ПК» не ловится до релиза.

**Практический вывод.** Оба пути живут одновременно и не конфликтуют: `docker-compose` в
репозитории остаётся как способ поднять весь стек локально (ваш сценарий), Vercel — обязательный
контур проверки (сценарий команды). Конфликт возможен только один — если код начинает зависеть
от того, где он запущен (`localhost` в ссылках, жёсткий порт, чтение файлов с диска). Этого не
должно быть: конфигурация приходит из переменных окружения, ссылки — относительные. Для теста бэкенд можно поднимать локально и пробрасывать туннелем, но для «проверить с
телефона» нужен постоянный адрес. Выбор сделан — **D-117**: Render free (750 ч/мес, 512 МБ, без карты,
засыпание 15 мин), резерв — Oracle Cloud Always Free (2 OCPU / 12 ГБ, не спит).
Fly.io free-тарифа больше нет, Koyeb закрыт для новых аккаунтов. Расчёт и ссылки — `docs/costs.md` §3.

## 5. Что считается «проверено» без Docker

| Изменение | Минимальная проверка |
|---|---|
| Логика денег, игры, API | `npm test` в `backend` (pg-mem), плюс типы `tsc --noEmit` |
| Схема БД | `init.sql` + `schema-check.sql` на Supabase `psql` (дважды) |
| Frontend | `tsc --noEmit`, `npm test`, `npm run build` |
| Сборка образов | только CI (`docker` job) — локально не требуется |
| Транспорт и документы | `npm run verify`, `npm run verify:node` |

Правило: если проверка возможна только в Docker, она должна быть **в CI**, а не в чек-листе
агента. Смешивать нельзя: «не смог проверить» тогда выглядит как «не проверял».
