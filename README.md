# 🏛️ VAULT — Telegram Mini App Игровая Платформа (v4)

Игровая платформа внутри Telegram с тремя игровыми режимами и системой пассивного дохода.
Валюта: **USDT (сеть TON)**. Единая комиссия: **10%** с игр, **1%** за вывод.

> Статус: ✅ Работающий MVP. Вся игровая математика, WebSocket-синхронизация, 3D-сцены, cron-задачи и админка реализованы.
> Демо-режим (`DEMO_MODE=true` по умолчанию) позволяет тестировать игры без реального TON;
> в реальном режиме демо-вход и демо-пополнение отключаются на сервере.
>
> Автоматические проверки: `backend: npm test` (7 режимов смоук-тестов), `npx tsc --noEmit`
> в backend/frontend/bot, схема БД на настоящем PostgreSQL и сборка Docker-образов —
> всё это запускает CI (`.github/workflows/ci.yml`).

## 🚀 Быстрый старт (3 способа)

### Способ 1: Docker Compose (рекомендуется для проверки)

```bash
git clone <repo-url> vault && cd vault
cp .env.example .env  # для демо можно не редактировать
docker compose up --build
```

Все режимы и секреты читаются из корневого `.env` (в compose нет зашитых литералов):
`DEMO_MODE`, `BOT_TOKEN`, `BOT_USERNAME`, `ADMIN_TELEGRAM_IDS`, `ADMIN_PASSWORD`,
`JWT_SECRET`, `SECURITY_PEPPER`, `ALLOWED_ORIGINS`, `POSTGRES_*`, порты. Полный список
и пояснения — в [`.env.example`](./.env.example).

Схема БД живёт в одном файле `backend/src/db/init.sql`; образ PostgreSQL собирается
из корня репозитория (`docker build -f db/Dockerfile .`) и копирует именно его.

**Примечание для Windows (Docker Desktop):**
Если получаете ошибку `user declined directory sharing`, убедитесь, что в **Docker Desktop → Settings → Resources → File Sharing** разрешён доступ к диску, где лежит проект (обычно `C:`). Конфигурация проекта использует собственный Dockerfile для PostgreSQL без bind-mount файлов с хоста, поэтому дополнительная настройка прав для конкретных файлов не требуется.

После запуска:
| Сервис | URL |
|--------|-----|
| 🌐 Frontend (Mini App) | http://localhost:3000 |
| 🔌 Backend API | http://localhost:8000/api/health |
| 🐘 PostgreSQL | `localhost:5432` (пользователь: `vault`, пароль: `vault_pass`, БД: `vault`) |
| ⚡ Redis | `localhost:6379` |

Демо-режим включён по умолчанию (`DEMO_MODE=true`): при входе через браузер создаётся тестовый пользователь, а кнопка «Демо-пополнение» на экране депозита мгновенно зачисляет средства для тестирования всех игр.

### Способ 2: Режим разработки (с hot-reload)

Требования: Node.js 20+, PostgreSQL 16+, Redis 7+.

```bash
# 1. Запустите Postgres и Redis (локально или в докере)
docker-compose up -d db redis

# 2. Бэкенд
cd backend
npm install
npm run dev  # запустится на http://localhost:8000

# 3. Фронтенд (в другом терминале)
cd ../frontend
npm install
npm run dev  # запустится на http://localhost:3000
```

Бэкенд будет автоматически подключаться к Postgres/Redis из `docker-compose`, а фронтенд проксирует запросы на `localhost:8000` (настроено в `vite.config.ts`).

### Способ 3: Запуск в Telegram боте

1. Создайте бота через [@BotFather](https://t.me/BotFather), получите токен
2. В `.env` укажите:
   ```env
   BOT_TOKEN=ваш_токен
   BOT_USERNAME=ваш_бот        # юзернейм того же бота, БЕЗ @
   WEBAPP_URL=https://ваш-домен
   ALLOWED_ORIGINS=https://ваш-домен
   ADMIN_TELEGRAM_IDS=ваш_telegram_id
   ADMIN_PASSWORD=сильный_пароль
   JWT_SECRET=<64 случайных символа>
   SECURITY_PEPPER=<другой случайный секрет>
   DEMO_MODE=false
   ```
3. Установите TON-переменные для реальных платежей (см. раздел [Интеграция с TON](#интеграция-с-ton))
4. Запустите стек: `docker compose up -d`

Вне демо-режима backend **не стартует** без `JWT_SECRET`, `SECURITY_PEPPER`,
`ADMIN_PASSWORD`, `BOT_TOKEN` и `ADMIN_TELEGRAM_IDS` — с демо-значениями секретов
можно подписать чужой JWT. `BOT_USERNAME` обязан совпадать с ботом из `BOT_TOKEN`:
по нему строятся реферальные ссылки `https://t.me/<BOT_USERNAME>?start=<код>`
(бот при старте сверяет его с `getMe()` и пишет предупреждение в лог).

## 🔌 API эндпоинты

Все эндпоинты (кроме `/api/auth/telegram`) требуют заголовок `Authorization: Bearer <JWT>`.

### Авторизация и профиль
| Метод | Путь | Описание |
|-------|------|----------|
| GET | `/api/config` | Публичная конфигурация: минимумы, комиссии, `demo_mode`, `bot_username` |
| POST | `/api/auth/telegram` | Авторизация: initData проверяется по HMAC (`WebAppData` + BOT_TOKEN) и возрасту `auth_date`; вход `demo:<id>` — только в `DEMO_MODE` |
| GET | `/api/profile` | Получить профиль пользователя (баланс, настройки, статистика) |
| PATCH | `/api/profile` | Обновить настройки (кошелёк вывода, автоненаправление в сейф, уведомления) |
| GET | `/api/transactions?limit=50` | История транзакций |

### Кошелёк
| Метод | Путь | Описание |
|-------|------|----------|
| GET | `/api/wallet/deposit-address` | Получить адрес для пополнения |
| POST | `/api/wallet/demo-deposit` | Демо-пополнение: 403 вне `DEMO_MODE`, потолок $10 000, тип транзакции `demo_deposit` |
| POST | `/api/wallet/withdraw` | Вывод (`{amount, pin, address}`): PIN обязателен всегда, возвращает `withdrawal_id` и `status` (`pending` в реальном режиме, `paid` в демо) |
| POST | `/api/wallet/set-pin` | Установить PIN-код вывода (4 цифры, bcrypt) |

### 🚀 Ракета
| Метод | Путь | Описание |
|-------|------|----------|
| POST | `/api/rocket/start` | Сделать ставку → `{round_id, replay_seed, max_bet}`. **Без `crash_at`** |
| GET | `/api/rocket/history?limit=50` | История только ЗАВЕРШЁННЫХ раундов (летящий раунд не отдаётся) |
| GET | `/api/rocket/replay/:id` | Реплей раунда; для незавершённого — 404 |
| GET | `/api/rocket/bankroll` | Текущий размер кассы |
| WS | `/rocket` | `rocket:launch` → `tick {multiplier, elapsed}` → `cashout` / `crash {crash_at}`; точка взрыва приходит только с событием `crash` |

## 🔧 Интеграция с TON

По умолчанию проект запускается в демо-режиме, где все переводы фейковые. Для подключения реальной сети TON нужно:

1. Создать кошелёк проекта, сохранить мнемонику
2. Деплоить USDT Jetton (использовать существующий в mainnet: `EQCxE6mUtQJKFnGfaROTKOt1lZbDiiX1kCixRv7Nw2Id_sDs` или сеть testnet)
3. Заполнить переменные в `.env`:
   ```env
   DEMO_MODE=false
   TON_API_KEY=ваш_ключ_от_toncenter_или_tonapi
   TON_WALLET_MNEMONIC=24 слова мнемоники проекта
   USDT_JETTON_ADDRESS=EQ...
   ADMIN_TELEGRAM_IDS=ваш_telegram_id
   BOT_TOKEN=токен_бота
   WEBAPP_URL=https://vault-app.com
   ```
4. Дописать логику в `backend/src/services/ton.ts`:
   - `startDepositListener()` — слушать входящие Jetton транзакции на кошельки пользователей, зачислять баланс
   - автоматическую отправку USDT вместо ручной выплаты оператором

**Как устроен вывод сейчас.** `processWithdrawal()` проверяет PIN (обязателен всегда,
обход `0000` устранён), одной транзакцией списывает деньги и создаёт заявку в таблице
`withdrawals`. В демо заявка сразу получает `paid` и демо-`tx_hash`; в реальном режиме —
`pending`, а оператор отправляет USDT вручную и вносит `tx_hash` в админке
(`POST /api/admin/withdrawals/:id/pay`). Отклонение заявки возвращает деньги на баланс.
Статус меняется только из `pending`, поэтому двойная выплата или двойной возврат
одной заявки невозможны. Выдуманный `tx_hash` в реальном режиме больше не возвращается:
раньше деньги списывались, а в блокчейн ничего не уходило.

Для автоматизации понадобятся `@ton/ton` и `@ton/crypto` (сейчас в `backend/package.json`
их нет — неиспользуемые зависимости удалены).

## Security and access control

### Безопасность и контроль доступа

- Telegram `initData` проверяется по официальному алгоритму: `secret_key = HMAC_SHA256("WebAppData", BOT_TOKEN)`,
  затем `HMAC_SHA256(secret_key, data_check_string)` сравнивается с `hash` через `timingSafeEqual`;
  `auth_date` старше 24 часов отклоняется. Вход `demo:<id>` работает только в `DEMO_MODE`;
- лимитеры денежных эндпоинтов стоят ПОСЛЕ авторизации и считаются по `user_id`
  (`authedRateLimit`): прежние ключевались заголовком `X-Device-Id`, который задаёт
  сам клиент, и снимались одной его сменой. Общий лимит 300 запросов/мин остаётся
  на device/IP — он защищает публичные маршруты;
- блокировка подбора PIN на 15 минут после пяти ошибок (Redis, при отказе Redis —
  память процесса), PIN обязателен для вывода всегда;
- доступ в админку: `ADMIN_TELEGRAM_IDS` (сравнение числами — `telegram_id` это BIGINT,
  а node-pg отдаёт его строкой) + `ADMIN_PASSWORD`; вне демо backend не стартует
  без секретов и без непустого allowlist;
- каждая изменяющая операция админки пишется в `admin_audit_log` с маскировкой
  `password`/`pin`/`mnemonic`;
- HMAC-хэши IP/устройств (pepper — `SECURITY_PEPPER`) находят общие идентификаторы
  у нескольких аккаунтов и создают флаги для ревью;
- один кошелёк вывода нельзя привязать к двум аккаунтам (частичный уникальный индекс);
- CORS HTTP и Socket.io ограничен `ALLOWED_ORIGINS` (у сокета больше нет `origin: '*'`);
- `crash_at` не отдаётся клиенту до завершения раунда; код сейфа — до момента открытия;
- денежные операции атомарны: захват строки (`UPDATE ... WHERE status=... RETURNING`)
  выполняется ДО движения денег, поэтому двойной клик не платит дважды;
- Redis координирует Socket.io между инстансами и выдаёт leases для cron и запуска раундов.

Секреты описаны в `.env.example`. Реальные проверки TON-кошельков остаются в этапе
интеграции блокчейна.

### Локальный вход в админку

Docker Compose передаёт `ADMIN_PASSWORD` в backend. Если корневого `.env` нет, локальный пароль — **`admin`**. Чтобы использовать свой пароль:

```bash
cp .env.example .env
# измените ADMIN_PASSWORD в .env
docker compose up -d --build backend frontend
```

После неправильного пароля обновите страницу админки: ошибочное значение удаляется из `sessionStorage`, и приложение запросит пароль снова. Строки `replace_with_...` в старом `.env.example` были обозначениями-заглушками, а не фактически переданными контейнеру значениями.

## Уведомления и жизненный цикл (этап 3)

В профиле независимо включаются уведомления Дуэлей, Сейфа, рефералов и Vault Вклада. Сервер проверяет настройки до сохранения и Socket.io-доставки; lifecycle-key защищает напоминания и результаты от дублей. Сейф сообщает участникам о приближении/старте взлома, результате и отмене; Vault — о дневной прибыли и выплате с предложением открыть новый вклад; реферальная система — о новом участнике и начислении.

Неактивный пользователь с доступным остатком предупреждается после 180 дней (порог `dead_balance_inactive_days`). Вход сбрасывает предупреждение. Если за следующие 7 дней входа нет, только `users.balance` переводится в распределяемый пул 💎 Vault Вклада и фиксируется транзакцией `dead_balance_vault`; frozen balance, Safe и активные Vault-вклады не затрагиваются.

### Стабильный приветственный экран

Первичный вход защищён single-flight блокировкой: повторный запуск React-эффекта не отправляет вторую авторизацию и не может ошибочно признать только что созданный аккаунт существующим. Пока onboarding открыт, игровые редиректоры, badges и модальные уведомления не монтируются и не меняют маршрут.

## Игровые реплеи и реванши (этап 4)

Завершённые Rocket, Duel и Safe доступны по публичному URL `/replay/{game}/{id}` и единому API `/api/replay/{game}/{id}` (`version`, `game`, `outcome`, `animation`, `participants`, `share_url`). Rocket сохраняет seed визуальной сцены, работает на server ticks 30 FPS и интерполируется браузером через `requestAnimationFrame` 60 FPS. Smoke-suite прогоняет 100 000 воспроизводимых раундов и проверяет RTP около 90% / house edge около 10%.

Реванш Дуэли адресован только прежнему сопернику. Он может принять или отклонить его; отклонение атомарно снимает резерв ставки. История игр и экраны результатов ведут в replay/share flow.

### Устойчивость браузерной сессии

Приватное дерево приложения монтируется только после получения JWT. Запоздалый `401` от старого запроса не может удалить новый токен, а `429` и временные сетевые/DB ошибки больше не считаются выходом из аккаунта. Общий rate-limit составляет 300 запросов/мин на устройство (или IP, если заголовка нет), поэтому Chrome и Firefox за одним NAT имеют независимые buckets; денежные эндпоинты лимитируются отдельно и по `user_id`. Polling сокращён в пользу Socket.io. Ответ `duel/accept` самодостаточен и позволяет показать корректную сумму результата даже при недоступности последующего replay GET.

### Публичные replay-карточки

Replay — не техническая отладка, а share landing. Параметр `player` выделяет отправителя ссылки; если его нет, героем становится победитель. Карточки показывают понятный денежный результат и CTA «Попробовать VAULT». Safe публикует рейтинг с вкладами, временем, призом и прибылью; Duel — обе стороны, победителя и приз; Rocket — ставку, точку кэшаута, выплату, чистую прибыль и финальную точку. Призрак после кэшаута — только визуал: внутренний флаг «красивого полёта» в публичный реплей не отдаётся (см. «UI-kit, карточка пользователя и лимиты» ниже).

Экран пополнения повторяет получение адреса после временных ошибок и предлагает ручной retry. Адресный реванш принимается/отклоняется непосредственно в центре уведомлений.

### Красивый полёт после кэшаута

Cashout немедленно завершает активный раунд и фиксирует выплату. На экране результата настоящая ракета приземляется, а полупрозрачный призрак по кривой `e^(0.075t)` продолжает путь до сохранённого `crash_at` и обязательно взрывается. Примерно в 3% ранних выходов (`beautiful_flight_chance`) финальная точка призрака поднимается до x20–x80 — это внутренняя механика, она не меняет выплату и **не показывается игроку**: ни в подписях, ни в API реплея. Replay использует те же `cashout_at`, `crash_at`, seed и кривую и воспроизводит сцену целиком.

Replay сохраняет контекст внутреннего перехода: кнопка «Назад» возвращает в Rocket, Safe или Duel, откуда открыта запись; для внешней share-ссылки fallback — главное меню. Safe-карточка формулирует чистый исход явно: «заработал», «потерял» или «вышел в ноль». В Rocket камера результата следует за призраком и показывает его текущий множитель рядом с уже зафиксированным кэшаутом.

История Rocket скрывает финальную точку только локально у автора текущего раунда, пока его призрак ещё летит. После взрыва, повторного входа в зал и у остальных пользователей `crash_at` виден сразу; replay при этом раскрывает его после собственной анимации. Возврат из внутреннего replay выполняется по browser history, не добавляя ещё один маршрут зала и не создавая навигационный цикл.

## UX и статистика (этап 5)

Главная оставляет основные денежные действия, игры, Vault и короткий статус Сейфа; публичные показатели вынесены в `/stats`. Экран Vault загружает фактический календарный журнал `/api/vault/accruals`. Админская reconciliation-карточка раскрывает нарушения и позволяет повторить проверку. Для Telegram viewport до 380 px/680 px используются компактные отступы и элементы. Актуальный 401 централизованно перезапускает auth bootstrap, поэтому приватные действия восстанавливаются без reload.

На главной используется единственная плитка перехода в статистику проекта — дублирующая карточка удалена.

## UI-kit, карточка пользователя и лимиты (ревизия интерфейса)

**Иконки вместо эмодзи.** `components/ui/Icon.tsx` — инлайновый набор SVG, наследующий цвет
текста: никаких внешних шрифтов, никаких «прыгающих» эмодзи и разной ширины на разных
платформах. Пользовательские эмодзи из компонентов убраны (в тостах — просто текст), кнопки
больше не кричат верхним регистром.

**Свои модалки вместо `confirm`/`prompt`.** `components/ui/Dialog.tsx` + `DialogHost` в `App.tsx`
закрывают все подтверждения и вводы (хром-окно админки, отмена вклада сейфа, ввод суммы,
копирование реф-кода и т.д.): нативные диалоги в Telegram WebView рисуются системным окном
поверх Mini App, а часть браузеров их просто блокирует. `window.confirm`/`window.prompt` в коде
не осталось.

**Карточка пользователя в админке.** `GET /api/admin/users/:id` — баланс, статистика по играм,
дуэли, сейф, вклад и **рефералы с именами** (оборот каждого и начисления рефоводу) одним
запросом: `LEFT JOIN … GROUP BY` вместо N+1 подзапросов. Строка «Заморожено (дуэли)»
переименована в «Дуэли» — в ней сумма ставок, а не замороженные деньги.

**Лимит ставки Ракеты.** `rocket_max_bet_percent` по умолчанию **100** (вся касса), диапазон
`[0, 1000000]`; **`0` — лимита нет**, тогда `/api/rocket/bankroll` отдаёт `max_bet: null`,
а экран Ракеты пишет «Макс: **без лимита**» вместо бессмысленного `$0`. Значения больше 100 —
осознанный риск админа (точка взрыва упирается в `bankroll / bet`). Сумма округляется
`roundDownClean()`, поэтому в подписи всегда «красивое» число.

**Взлом сейфа в 18:00 МСК** (`safe_crack_hour=18`, было 21): окно взлома, дедлайн и подпись
`crack_at_msk` считаются от той же настройки; существующие БД переводит миграция в `src/index.ts`.

**Деньги на экранах.** Единый `BalancePanel` («доступно» + пилюли frozen/сейф/вклад) на
`/deposit`, `/withdraw` и в играх вместо разнобойных строк «Текущий баланс: $50.00 ❄️ Заморожено…».
Кнопки быстрого выбора суммы (`AmountChips` + `utils/betChips.ts`) считаются от доступного
баланса (25/50/75% + «Всё») и округляются вниз до первой значащей цифры — те же «красивые»
числа, что и в лимите Ракеты. Служебная сноска «Комиссия игр · Вывод · USDT (TON)»
(`PlatformFootnote`) берёт цифры из `/api/config` и не спорит с контентом цветом.

**Реплеи.** Подпись «✨ Красивый полёт… призрак долетел до ×N» и поле `was_beautiful` удалены —
внутренний шанс 3% игроку не виден. В реплеях появился звук: `sfx.unlock()` на первом жесте
создаёт `AudioContext` (без него браузер молчит, а в живом раунде звук был). Дуэль в реплее
показывает чистую прибыль (`profit = prize − amount`): при ставке $50 и призе $70 — «+$20».

**Сессия и демо-пополнение.** JWT дополнительно держится в памяти вкладки: в приватном режиме и
в WebView с заблокированными хранилищами `sessionStorage` бросает SecurityError, токен
«исчезал» сразу после входа, и демо-пополнение отвечало «Ошибка авторизации» до перезагрузки
страницы. Теперь `Deposit` при 401 ждёт восстановления сессии и повторяет запрос один раз
(отклонённый по авторизации запрос деньги не начисляет).
